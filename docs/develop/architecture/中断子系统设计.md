## 1. 背景

当前内核的中断处理是**平台各自为政**的：

- CPU 异常与外设中断**共用一张表** `exception_handlers[EX_*]`（`duck/kernel/exceptions.c:12`），
  枚举 `EX_RESET…EX_PERMISSION`(1-8) 与 `EX_TIMER/KEYBOARD/MOUSE/AUDIO/NONE/DMA/I2C`(9-15) 同级
  （`duck/arch/interrupt.h:19-35`）。
- **一个 EX 槽只能挂一个 handler**，后注册静默覆盖（`duck/modules/perf/perf.c:483-484` 备份并覆盖
  `schedule` 注册的 `EX_TIMER`）。
- **IRQ 号 → 逻辑号** 靠 13 个平台文件里各写一段 `if/else` 链（`platform/*/init.c` 的
  `interrupt_get_source()`），写法/默认值/未知中断处理**全都不一样**。
- **未知中断被当作 `EX_TIMER` 派发**（`platform/v3s/init.c:261` 把 `no` 预置为 `EX_TIMER`），
  实测 v3s 上未处理的 USB OTG_Device(IRQ 103) 会持续触发并刷屏，只能靠"只打前 8 次"限流掩盖。
- **没有 mask/disable API**：`gic2.h` 里有 `icenable[]` 字段、raspi5 头文件里有
  `GICD_ICENABLER` 宏，但全仓没有任何代码写过它们；只有 raspi3 平台手写过 `IRQ_DISABLE1/2`。
- **没有 bottom-half**：重活（cache 维护、环形缓冲、重启 DMA）直接在中断上下文里做
  （`sound/t113-s3.c:564-628`、`sound/v3s.c:745-787`）。
- **EOI 责任不清**：平台有的分支 ack、有的不 ack，框架又在 IRQ 返回时无条件"补一刀"
  （`exceptions.c:106-111` + 平台 `interrupt_last_irq`）。
- 平台差异被硬编码：v3s 因为 GICC_DIR 页未映射，专门写了 `gic_irqack2()` 绕开通用 `gic_irqack()`
  （`platform/v3s/gic.c:200-218`）。
- 一致性 bug：keyboard/t113 **使能 `IRQ_GPIOB_NS`(101) 却 ack `IRQ_GPIOB_S`(102)**；
  `dwc2_irq_handler` 写好了但注册被注释掉（`usb/dwc2.c:761`）。
- 文档里已许诺但未实现：`interrupt_register(u32 no, interrupt_handler_t, void*)`
  （`docs/develop/api/api-reference.md:131`）。

## 2. 目标 / 非目标

**目标**

1. 驱动**按真实 IRQ 号**注册，不再修改平台文件；
2. 支持**共享中断**（一号多 handler）与 **tick 通知**（消除"覆盖 EX_TIMER"这类问题）；
3. 提供 `mask/unmask/enable/disable/优先级/触发类型` 的**统一 API**；
4. 未注册中断有**明确策略**：计数 + 一次性告警 + 自动 mask；
5. **bottom-half** 机制：中断里只清状态 + 排队，重活推迟到退出中断前（或线程）；
6. **可诊断**：每 IRQ 计数/名字/状态，可 dump（`irq_dump()`，后续导出 `/dev/irq`）；
7. **跨平台**：控制器抽象为 `irq_chip`，平台只注册 chip 与 IRQ 号宏。

**非目标（本期不做）**

- 中断嵌套（沿用"进入 IRQ 期间关中断"的现状）；
- SMP 亲和性/跨核 IPI（只留 `set_affinity`/`send_ipi` 接口）；
- 动态加载中断控制器（本仓库无内核模块动态加载）。

## 3. 关键设计决策

### 3.1 中断核心必须放内核，不能做成 module

本仓库的 "module"（`duck/modules/*`）不是可加载 `.ko`，而是：

- **静态链接**进内核镜像（各级 `ya.py` 都是 `set_kind("static")` + `add_deps('kernel')`）；
- 由 `module_t{init,exit}` 描述，**注册点在 `app/init/module.c`**（编译进 init 内核应用，
  `:219 module_run_all()`）。

因此"做成 module"的含义是：**可选、可被 init 裁剪、且初始化较晚**。

启动顺序（`duck/kernel/kernel.c:22-70`）：

```
log_init → exception_init → page_init → syscall_init → schedule_init ← 这里就 timer_init() 开中断
        → module_init → memory_init → vfs_init → thread_init → event_init
        → （之后 init 应用）module_run_all()  ← 各 module_t->init
```

结论（四条判据）：

| 判据 | IRQ 核心 | 结论 |
|---|---|---|
| 被异常/中断路径引用 | `exceptions.c:76-80`、各 arch 的中断入口 | 放 module ⇒ arch/kernel **反向依赖** module，需弱符号/函数指针 |
| 必须早于 `module_run_all()` | 是（tick + 早期 SD/UART 中断） | 必须内核 |
| 是否每个平台都必须有 | 是（所有驱动依赖） | 核心服务不该可选 |
| 静态链接下空间/性能 | 无差别 | "模块化省资源"不成立 |

且本仓库已有约定：`schedule/exceptions/thread/vfs/device/memory/page` 在内核，
`dma/gpio/net/sound/mmc/keyboard` 是模块 —— IRQ 核心与调度器同级。

### 3.2 主流 OS 对照

| 系统 | 核心在哪 | 控制器（irqchip）在哪 | 驱动能否模块化 | 下半部形态 |
|---|---|---|---|---|
| Linux | `kernel/irq/`（永不模块化） | `drivers/irqchip/`，`IRQCHIP_DECLARE` 早期注册 | 能（`request_irq` 导出） | softirq / tasklet / threaded IRQ |
| FreeBSD | `kern/kern_intr.c` | `sys/arm/.../gic.c`（编译进内核） | 能（`bus_setup_intr`） | `swi_*` / taskqueue |
| Windows NT | HAL（内核一部分） | HAL 内部 | 能（`IoConnectInterrupt`） | ISR → DPC |
| macOS/XNU | Mach 中断桩 + platform expert | 内核内 | 能（IOKit kext） | 过滤 ISR + 工作循环线程 |
| Solaris | `uts/common/os` | 内核内 | 能（`ddi_add_intr`） | `softint` |
| QNX Neutrino | 内核提供 `InterruptAttach*` | 内核内 | **用户态驱动** | `InterruptAttachEvent` → 用户线程 |
| seL4 | 内核只有 IRQ 对象 + `Ack` | 最小 | 全用户态 | 用户线程 |
| Fuchsia/Zircon | 微内核 `zx_interrupt_*`（mask/EOI 内核代持） | 内核 | 用户态驱动 | 端口/等待队列 |
| Zephyr | 单镜像 `IRQ_CONNECT()` 编译期表 | 编译期 | 无动态模块（`zephyr/module`＝源组合） | `k_work` |
| FreeRTOS/ESP-IDF | ISR 全在镜像内 | 镜像内 | 无 | `*FromISR` 队列 |
| RT-Thread | 中断核心固定在 kernel | 内核 | 有 `.mo` 但仅应用/驱动层 | 软中断/工作队列 |

归纳为四种分层：

1. **宏内核**（Linux/BSD/XNU/Solaris/NT）：核心在内核；控制器驱动早期注册；设备驱动可模块化。**主流**。
2. **微内核**（QNX/seL4/Zircon）：内核只做 mask/EOI/投递，策略与处理在用户态。
3. **单镜像 RTOS**（Zephyr/FreeRTOS/ESP-IDF）：中断表编译期生成，无模块概念。
4. **混合**（Linux 实际形态）：核心 + 内建控制器 + **外挂控制器作为普通驱动运行期挂接**。

> 没有任何主流系统把中断核心做成可加载模块。RT-Thread 有内核模块机制，但中断核心仍固定在 kernel。

### 3.3 本仓库的落地形态（方案 C）

```
duck/kernel/irq.c / irq.h                ← 核心（desc 表/注册/派发/EOI/BH/统计）★必须在内核
duck/libs/include/archcommon/irq_chip.h  ← 控制器抽象（struct irq_chip）
duck/libs/libarchcommon/arm/gic2.c       ← GICv2 chip + 缺失的 mask/unmask/set_type
duck/platform/v3s/gic.c                  ← v3s chip 变体（eoi=gic_irqack2，收编 GICC_DIR 差异）
duck/modules/intc/                       ← 【可选·未来】外挂控制器（GPIO 中断扩展、MSI…）
duck/modules/irqstat/                    ← 【可选·未来】诊断：/dev/irq + shell `irq` 命令
```

"模块化"的正确落点是：**外挂控制器**与**诊断导出**（可选、可裁剪、不在关键路径）。

## 4. 架构分层与依赖方向

```
① 异常向量层（不改）   arch/<arch>/interrupt.c    CPU 向量、interrupt_context_t、interrupt_exit_ret
② 异常分类层（瘦身）   kernel/exceptions.c        保留 CPU 异常类；EX_IRQ 变成"进中断"入口标记
③ 中断核心（新增）     kernel/irq.c               desc 表/注册/派发/统计/未处理策略/BH
④ 控制器抽象（新增）   libs/include/archcommon/irq_chip.h + 各控制器实现
⑤ 平台落地（极薄）     platform/<soc>/            注册 chip + IRQ 号宏（irq_set_tick）
⑥ 驱动                 irq_register / irq_enable / irq_request_bh
```

依赖方向：**kernel 不依赖 platform/控制器名**（运行时由平台 `irq_chip_register()` 注册对象）。

## 5. 数据结构与 API

### 5.1 控制器抽象 `archcommon/irq_chip.h`

```c
#define IRQ_TYPE_LEVEL_HIGH 1
#define IRQ_TYPE_LEVEL_LOW  2
#define IRQ_TYPE_EDGE_RISING 3
#define IRQ_TYPE_EDGE_FALLING 4
#define IRQ_CHIP_EOI_AT_CLAIM (1u << 0)   /* get_active() 本身完成 ack（raspi5 型）*/

struct irq_chip {
  const char *name;
  u32 (*get_active)(void);                    /* claim 型：GIC 读 IAR、PLIC claim */
  int (*for_each_pending)(int (*cb)(u32, void*), void *arg);  /* 位图型：BCM/PL190/VIC */
  void (*ack)(u32 irq);
  void (*eoi)(u32 irq);                       /* NVIC/ESP32 型填 NULL（硬件自动）*/
  void (*mask)(u32 irq);
  void (*unmask)(u32 irq);
  void (*set_priority)(u32 irq, u32 prio);    /* 语义透传，不承诺统一量纲 */
  void (*set_type)(u32 irq, u32 type);
  void (*set_affinity)(u32 irq, u32 cpu);     /* 单核留 NULL */
  void (*send_ipi)(u32 cpu, u32 irq);         /* 单核留 NULL */
  u32 flags;
};

int  irq_chip_register(struct irq_chip *chip, u32 irq_base, u32 irq_num);
void irq_set_tick(u32 irq);
```

**所有回调允许为 NULL，框架调用前判空。**

### 5.2 核心 API `kernel/irq.h`

```c
#define IRQ_FLAG_SHARED       (1u << 0)
#define IRQ_FLAG_NO_AUTO_MASK (1u << 1)
#define IRQ_FLAG_CASCADE      (1u << 2)

typedef int (*irq_handler_t)(u32 irq, void *arg);   /* 1=已处理，0=不是我的 */

int  irq_register(u32 irq, irq_handler_t fn, void *arg, const char *name, u32 flags);
int  irq_unregister(u32 irq, irq_handler_t fn, void *arg);
int  irq_enable(u32 irq);   int irq_disable(u32 irq);
int  irq_mask(u32 irq);     int irq_unmask(u32 irq);
int  irq_set_priority(u32 irq, u32 prio);
int  irq_set_type(u32 irq, u32 type);
int  irq_set_affinity(u32 irq, u32 cpu);
u32  irq_get_count(u32 irq);
const char *irq_get_name(u32 irq);
int  irq_in_interrupt(void);
void irq_warn_once(u32 irq);      /* 取代各处"只打前 N 次"hack */
void irq_dump(void);

typedef void (*irq_bh_fn)(void *arg);
int  irq_request_bh(irq_bh_fn fn, void *arg);
void irq_bh_poll(void);

/* 供 arch 入口/平台调用 */
int  irq_core_enabled(void);                       /* 未注册 chip ⇒ 回落老路径 */
void irq_claim_and_dispatch(interrupt_context_t *ic);
void irq_dispatch_ctx(u32 irq, interrupt_context_t *ic);
void irq_dispatch(u32 irq);                        /* = dispatch_ctx(irq, NULL)，供向量型平台 */

struct irq_action { irq_handler_t fn; void *arg; const char *name; struct irq_action *next; };
struct irq_desc {
  struct irq_action *action;   /* 共享中断链 */
  struct irq_chip *chip;
  u32 count, unhandled, spurious;
  u8  masked, enabled, logged, flags;
};
```

### 5.3 号段与规模

- `IRQ_NUM_MAX`：平台可覆盖（v3s 建议 160 = 16 SGI + 16 PPI + 125 SPI；默认 256）。
- `IRQ_CHIP_MAX`：4（多控制器/级联用），每个 chip 带 `irq_base/irq_num`。
- IRQ 号语义统一为"**平台唯一 IRQ 标识**"：ARM=控制器号、x86=向量号、Cortex-M=IRQn，
  各平台在 `platform/<soc>/irq.h` 提供 `IRQ_*` 宏，驱动代码因此可跨平台复用。

## 6. 派发流程

```
IRQ 向量 → interrupt_entering_code(EX_IRQ) → exception_process(ic)
  └─ ic->no == EX_IRQ ?
       ├─ irq_core_enabled() ?  ── 否 ─→ 老路径 interrupt_get_source()（未注册 chip 的平台原样）
       └─ 是:
            irq_claim_and_dispatch(ic)
              ├─ 主 chip->get_active() 取号（claim 型） / for_each_pending（位图型）
              ├─ 号 >= 1020 ⇒ spurious++ ，eoi，返回
              ├─ irq == tick_irq ⇒ 走 EX_TIMER 槽（保持 do_schedule 需要 ic / perf 覆盖等行为）
              ├─ desc->action == NULL ⇒ unhandled++ + irq_warn_once + 自动 mask（可关）
              ├─ 依次调用 action 链，第一个返回 1 即停（共享中断）
              ├─ d->count++；无人认领 ⇒ unhandled++ + irq_warn_once
              ├─ chip->eoi(irq)  ← 框架是 EOI 的唯一所有者
              └─ irq_bh_poll()   ← 退出中断前执行 bottom half
            return ic           ← 已 EOI，不再走 interrupt_ack_pending()
```

保留 `interrupt_ack_pending()`（`exceptions.c:106-111` 与"中断内再异常"兜底），不动。

**约定（写进头文件注释）**

1. handler 必须**先清设备状态（W1C）**再排队重活；
2. 禁止在 handler 里用 `log_*`（可能走 vfs，非中断安全），需要时用 `irq_warn_once()`/`kprintf`；
3. 电平中断不清状态 ⇒ 框架的自动 mask 会把它关掉并告警（这正是 IRQ 103 场景的正确处理）；
4. 进入 IRQ 期间 CPU 关中断（不嵌套）；IRQ 栈上不做上下文切换
   （`context_irq_preemptible()` 对 IRQ 模式返回 0），tick 只置 `need_resched`。

## 7. bottom-half 与 threaded IRQ

- **BH 队列**（本期）：`irq_request_bh(fn, arg)` 在中断里入队，`irq_bh_poll()` 在 IRQ 退出前执行
  （仍在关中断上下文，语义与"直接在 ISR 里做"等价，但结构清晰、为线程化留口）。
  队列满时**就地执行**并计数 `bh_overflow`。
- **threaded IRQ**（后续可选）：中断里只 `mask + event_wakeup_io()`（`duck/kernel/event.h` 已有），
  重活在驱动线程里做 —— 即 QNX `InterruptAttachEvent` / Zircon 的思路，适合网络 RX、存储等重驱动。

## 11. 风险与取舍

| 风险 | 处置 |
|---|---|
| 切换到新路径后，未迁移的 IRQ 会被"未注册 ⇒ 自动 mask"打掉 | S2/S3 必须**同批完成**该平台所有在用的 IRQ（v3s 只有 DMAC 82 + TIMER0 50） |
| 优先级量纲各控制器不同（GIC 0 最高、NVIC 数值小最高、8259 固定） | `irq_set_priority` 只透传，文档写清，不承诺统一语义 |
| 中断里日志阻塞（115200 下 ~1ms/条） | 统一走 `irq_warn_once()`；禁止 `log_*` |
| 共享中断的"认领"语义 | 约定 handler 返回 1=已处理；全部返回 0 ⇒ 计 `unhandled` 并告警 |
| 级联控制器 | 用号段注册多 chip + `IRQ_FLAG_CASCADE`（handler 内允许再次 dispatch） |
| SMP/嵌套 | 本期不做，只留接口；沿用"IRQ 期间关中断、不在 IRQ 栈上切换" |

### 11.1 实施中实际踩到/必须处理的坑（S1~S3）

1. **`do_schedule()` 会返回"切换后的新上下文"**（时钟抢占）。因此派发入口不能
   `irq_claim_and_dispatch(ic); return ic;` —— 必须把 handler 的返回值一路透传回
   `exception_process()`，否则时钟抢占被静默丢掉。已把 `irq_dispatch_ctx()` /
   `irq_claim_and_dispatch()` 的返回值改成 `interrupt_context_t *`。
2. **临界区不能是 `cpu_cli()` + `cpu_sti()`**：`cpu_sti()` 无条件开中断，而
   `irq_chip_register()` 是在 `kernel_init()` **中段**（`schedule_init → timer_init`）
   被调用的，后面还有 `memory_init/thread_init` 没跑完；提前开中断会让 tick 打进来，
   而 `do_schedule()` 在 `current_thread == NULL` 时**提前返回、不调 `timer_end()`**
   ⇒ 定时器挂起位没人清 ⇒ 电平中断反复重投递 ⇒ 启动被风暴卡死。
   现在用 `mrs/msr CPSR` 保存/还原（`irq_save_flags/irq_restore_flags`）。
3. **注册顺序**：必须先 `irq_set_tick()` 再 `irq_chip_register()`。反过来的话，
   两者之间的窗口里若有中断进来，`IRQ_TIMER0` 会被当成"未注册号"而**自动 mask**，
   时钟永久停掉。
4. **`irq_chip_register()` 要幂等**：开了 `MP_ENABLE` 的平台每颗 CPU 都会走
   `kernel_init()` 的 else 分支 → `schedule_init()` → `timer_init()`，同一个 chip
   会被注册多次。
5. **`exception_handlers[]` 的类型 bug（既有问题）**：`interrupt_handler_t` 本身已是
   函数指针，数组却声明成 `interrupt_handler_t *`（多一层）。原来在 `exceptions.c`
   里靠隐式转换"侥幸能跑"，一旦在别处**调用**就报
   `called object is not a function or function pointer`。已统一修正
   （`exceptions.c` 定义、`exceptions.h` 声明、`perf.c` extern 三处）。
6. **`interrupt_last_irq` 要跟着新路径更新**：老路径由 `interrupt_get_source()` 记录，
   新框架下改由平台的 `get_active` 回调记录（v3s 的 `v3s_gic_get_active()`），
   否则 `interrupt_ack_pending()`（中断内再异常时的兜底 EOI）会写一个过期的号。
7. **OOB 防护**：GIC 的 1022/1023（spurious）在 `irq_valid()` 之外，必须先判
   `>= 1020` 再访问 `desc[]`，否则 `spurious++` 会写出界。

### 11.2 实施中踩到的坑（S4 / 诊断出口阶段，2026-09-19）

8. **打印路径坏了，"观察"本身就会失真 —— 这条排障教训比 bug 本身重要**：
   raspi3 曾稳定"卡在 `BUILD_TAG` 之后、0/10 起不来"。真因与中断无关：`kprintf` 的
   2KB `printf_buffer` 是**所有 CPU 共用**的，抢锁失败（有界自旋会主动放弃）时两个 CPU
   并发写同一块缓冲 ⇒ 字符串失去 `'\0'` ⇒ `kstrlen` 读到天文数字 ⇒ 疯狂打印垃圾
   （PC 老落在 `kprintf/kmemset` 区域，看起来就像"卡死在日志里"）。
   改成 **per-CPU 槽位**后 raspi3 **10/10 进 shell**。
   —— 教训：**统一中断框架的排障全靠串口日志**，日志不可信时，所有测量都要打问号；
   这也是"诊断出口必须尽早做"的理由（`/dev/irq`）。
9. **格式化必须有界，且判据要基于"剩余空间"**：`printf_buffer` 紧邻 `print_lock`
   （实测两符号相距正好 2048 = `KPRINT_BUF`），越界写会直接把打印锁写坏 ⇒ 整机日志停摆。
   于是补了 `kvsnprintf/ksnprintf`（`vsnprintf` 语义）。**第一版用"固定预留 160 字节"当判据，
   导致 64 字节缓冲输出空串**（固定预留 > 缓冲区），必须改成按 `room-5` 之类"剩余空间"夹紧。
   宿主侧带 canary 的单元测试抓到该问题；`serial_printf` 的 5 处"无界写 1024 字节栈缓冲"
   一并改为有界。
10. **镜像里仍有"越界写、受害者随 `.bss` 布局变化"的隐患（未查清）**：
   新增模块的 `.bss` 用 2048 字节 ⇒ raspi3 **0/5 挂**；改成 1024 ⇒ **3/3 正常**。
   同类问题已抓到过两次（`printf_buffer`→`print_lock`、栈溢出打到 `.bss` 里的 `_stack_other`），
   但**这次的具体越界者还没找到**。`modules/irq` 的 `irq_buf` 因此刻意用 1024，并在注释里写明。
   ⇒ 待办：对"好/坏"两个构建做 `.bss` 符号布局 diff，定位跨过好坏边界的变量。
11. **"早期 tick"风暴：根因是 `irq_save_flags/irq_restore_flags` 在 ARM64 会无条件开中断**
    raspi3 切到新框架后**稳定起不来**（0/5）。两个症状：
    ① `schedule current is null` 刷 644 行；
    ② 之后是 `exception no 5: UNDEF` 刷屏（`pc` 落在 `uart_send` 里，即"中断路径里的打印"）。
    **根因（只有一个）**：这对原语当时是
    `#if (ARMV7_A||ARMV7||ARMV5) && !ARM64 … #else { cpu_cli(); } { cpu_sti(); } #endif`
    —— **ARM64 落到 `#else`，`cpu_sti()` 是"无条件开中断"**。于是迁移后
    `timer_init()` 里的 `irq_chip_register()` → `irq_unlock()` **顺手把 CPU 中断打开了**，
    tick 立刻打进来；而 `do_schedule()` 在没有 `current_thread` 时直接 return、
    **连 `timer_end()` 都不调** ⇒ 定时器中断永不清 ⇒ 自动重装的定时器立刻重投递 ⇒ 风暴。
    **修法（两步，都必要）**：
      a) **补 ARM64 的真正实现**（本项根因）：`mrs daif` 保存、`msr daifset, #3` 关
         IRQ/FIQ、`msr daif, x` 按原值写回 —— 这样 `irq_unlock()` 不再改变原有中断状态，
         与原路径（老 `interrupt_get_source()` 根本不调这套原语）行为一致；
      b) `do_schedule()` 在 `current_thread == NULL` 时也要 `timer_end()`（只写定时器
         寄存器，不需要线程上下文）+ 继续 tick 计数 —— 防御性兜底：以后再有任何
         "tick 来早了"的路径都不会演变成风暴。
    **一个走过弯路、值得记下的教训**：曾试过"`kernel_init()` 的 `cpu==0` 段全程关中断"
    （`irq_save_flags/irq_restore_flags` 包住整段）。**实测证明它不必要 —— 撤销后 raspi3
    仍 5/5 进 shell**。改共享代码的中断时序、去掩盖一个"原语实现错"的问题，是错误的方向；
    正确做法是把原语本身修对（a）。
12. **`first dispatch` 的一次性标记有竞态（纯观感）**：多核同时首次派发各自的 tick 时，
    几颗 CPU 可能都读到 `desc[].seen == 0` ⇒ 同一行打印 2~3 次（raspi3 实测 3 次）。
    信息本身没错、也不影响功能；要消除只需把该标记换成原子置位。

13. **S4 的验收要"确定性"**：不等硬件真的来中断（时序不可控），而是
   `irq_enable(103)` + **合成派发** `irq_dispatch_ctx(103, NULL)`，再回读 `desc` 断言
   `unhandled >= 1 && logged == 1 && masked == 1` ⇒ 打 `PASS/FAIL`。
   `unhandled` 用 `>= 1` 而非 `== 1`：真机 103 可能在自检前先来过一次（那是历史现象本身）。
   用户态侧用 `cat /dev/irq` 交叉验证（该号 `UNHANDLED=1 MASK=1`）。
