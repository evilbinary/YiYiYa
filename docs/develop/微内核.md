# 微内核（foot 服务框架）

YiYiYa 提供微服务级别的支持：一个服务可以是一个程序、一个 so、一个设备驱动、一个函数。
可以开多个服务、负载均衡，也可以多个版本同时开。内核除了调度 CPU，也负责服务的资源仲裁。

> 本文是设计文档，描述 **foot**（原 gaga）服务框架的目标模型、当前实现与迁移路径。
> 代码：内核 `duck/modules/foot/`、用户态库 `eggs/libfoot/`、服务与驱动 `foot/service/`、`foot/driver/`。

---

## 一、设计初衷

传统微内核的服务调用要走两次 IPC（A→内核→B，返回再一次），每次都是一次陷入。
foot 的思路是把**参数与返回值放在共享内存里**，双方各自在自己的地址空间直接读写同一块物理页：

```
a 调 b：写共享页 → b 在自己的线程里取到 → 直接执行 → 写回结果
```

- 内核只负责「建共享页 + 通知有消息」，不参与每次的数据搬运 ⇒ 没有数据拷贝开销
- 同一物理页可以映射给多个服务 ⇒ 支持一个请求多个订阅者（广播）、多实例负载
- 服务注册后按名字查找 ⇒ 应用不需要知道服务在哪个进程

这仍然是 IPC（不是真的函数调用），但数据零拷贝、且可以把「提交」与「完成」解耦成异步队列，
这一点对图形/GPU 这类「一帧几十次小请求」的场景尤其重要。

## 二、总体架构

```
┌──────────────────────────────────────────────────────────┐
│ 应用 / 桌面（x11、weston、app/*）                          │
└───────────────┬──────────────────────────────────────────┘
                │ libfoot: client_regist / client_get / client_call
┌───────────────▼──────────────────────────────────────────┐
│ 服务与驱动（foot/service、foot/driver/*）                  │
│   systemd（资源服务）  vfsd  servicea/b                   │
│   csudusb（USB 主机栈）  wifi  bluetooth  tinyusb          │
└───────────────┬──────────────────────────────────────────┘
                │ ioctl(/dev/foot) + 共享页
┌───────────────▼──────────────────────────────────────────┐
│ 内核 foot 模块（duck/modules/foot/）                       │
│   · 客户端表 clients[]（名字 / id / tid / 状态）           │
│   · 共享页分配与跨进程映射（service_map_client_api）        │
│   · 资源仲裁：MMIO 窗口、DMA arena、中断事件（规划）        │
└──────────────────────────────────────────────────────────┘
```

分层原则：**内核只做「登记 / 授权 / 建共享页 / 唤醒」，不解释消息内容**。
消息语义由服务自己定义，新增服务不需要改内核。

## 三、调用模型

### 3.1 当前实现（共享页 + 状态机）

共享结构（`duck/modules/foot/service.h:59-81`）：

```c
typedef struct api {
  int cid;                  /* 调用 id（谁发起） */
  int state;                /* API_INIT/READY/RETURN/FINISH */
  char* fn;                 /* 方法号 */
  void* ret;                /* 返回值 */
  char args[MAX_ARGS_BUF];  /* 128 字节参数区 */
} api_t;

typedef struct client {
  char* name;
  int tid, id, cid, token, fd, service_id, type;
  int api_size;             /* 槽位数（当前恒为 1） */
  api_t* apis;              /* 指向共享页 */
  int state, count;
  struct client* instance[MAX_INSTANCE];
} client_t;
```

建立过程（`service.c:71-105`）：

1. 服务方 `client_regist("name")` → ioctl(SYS_NEW_CLIENT) → 内核 `kmem` 分配 `client_t`，
   `apis = sys_mmap2(NULL, PAGE_SIZE, MAP_ANON)` 建一页共享页
2. 调用方 `client_get("name")` → 内核 `page_v2p(服务方页表, apis)` 拿物理页，
   在调用方页表里 `page_map_on(..., PAGE_USER)` 映射成调用方 VA
3. 之后双方都读写同一物理页，`state` 做握手

调用方（`eggs/libfoot/client.c:12-61`）：找 `cid==0` 的槽 → 写 args → `state=API_READY` → **忙等**。
服务方（`client.c:69-97`）：`client_run()` 里轮询所有槽，遇到 `API_READY` 就执行 `fn` → 写 `ret` → `state=API_RETURN`。

### 3.2 目标模型：快路径 + 慢路径

| 路径 | 条件 | 行为 |
|---|---|---|
| **快路径** | 共享 ring 有空位、服务方 alive | 写消息 + 原子推进 `tail`，**不陷内核** |
| **慢路径** | ring 满 / 需要阻塞等结果 | `SYS_FUTEX` 睡在 ring 的某个地址上，服务方 `FUTEX_WAKE` |

要点：

1. **环形队列代替定长槽**：`foot_msg_t` 数组 + `head/tail`（单生产者单消费者用两个原子变量即可，
   多生产者需要 CAS 或一个 ticket 锁）。
2. **请求/响应按 `cid` 配对**：调用方分配 `cid`（单调递增），响应里带回同一个 `cid`，
   这样支持**乱序完成**（GPU 天然乱序）。
3. **不阻塞的提交**：`foot_submit()` 只入队并返回 `cid`；`foot_wait(cid, timeout)` 才等结果。
   图形栈一帧可以攒 N 条命令一次提交（批量）。
4. **超时**：每个等待都带墙钟上限，超时返回 `FOOT_ETIMEDOUT`，**不允许无超时死等**
   （当前 `client.c:45-56` 没有超时，服务崩溃会让客户端永久挂死）。

消息格式（建议）：

```c
#define FOOT_MSG_MAX 240
typedef struct {
  u32 cid;        /* 请求 id，响应原样带回 */
  u32 type;       /* 方法号 */
  u32 flags;      /* 同步/异步、是否需要唤醒 */
  u32 status;     /* 响应：0=OK 或 errno */
  u32 len;        /* payload 有效长度 */
  u8  payload[FOOT_MSG_MAX];
} foot_msg_t;
```

大对象（画布、显存、DMA 缓冲）不放进 payload，只放**句柄**（BO id / arena id / 共享页 id），
由资源接口（第五节）单独授权。

### 3.3 并发约束

- 一个服务默认单线程处理请求（`client_run` 串行），**但可以多实例**（`client_regist` 多次同名 = 多个服务线程）
- 服务内部若需要并发，自己起线程，foot 不限制
- 内核 `clients[]` 最多 `MAX_CLIENTS=100`（`service.h:32`），槽位生命周期必须可靠回收

## 四、服务注册与发现

| 接口 | 语义 | 实现位置 |
|---|---|---|
| `client_regist(name)` | 注册服务（可同名多次 = 多实例） | `client.c:122` → `service.c:174` |
| `client_get(name)` | 按名字拿第一个存活实例 | `client.c:146` → `service.c:162` |
| `client_id(id)` | 按 id 拿服务 | `client.c:169` → `service.c:195` |
| `client_run(client, fn)` | 进入服务循环（阻塞） | `client.c:69` |
| `clirent_un_regist(client)` | 注销 | `client.c:192` |

设计要求：

1. **代次（generation）**：`id` 会被回收复用，客户端缓存 id 时必须带 generation，
   否则服务重启后旧 id 会连到新服务上（协议版本不匹配的经典事故）。
2. **健康状态**：`service_get_client_name` 已经用 `thread->state != THREAD_STOPPED` 过滤死亡实例
   （`service.c:27-36`），但**实例数组没有上限检查**，必须补。
3. **注销必须可重入**：等所有在飞请求完成或超时后再摘除名字，否则客户端拿到已释放的共享页。
4. **服务声明**：服务在注册时声明自己支持的方法号与所需资源（可选，用于客户端发现能力）。

## 五、资源授权（capability 模型）

用户态驱动要能工作，只需要三样东西：**MMIO 窗口、DMA arena、中断事件**。目前只齐了第一样。
而这三样（以及服务本身）都必须用 **capability（能力句柄）** 授权，不能让用户态自己指定资源。

### 5.1 为什么必须用 cap

现状的 `sys_thread_map(tid, virt, phys, size, attr)` 直接吃用户态给的 `phys`，不校验范围：

```c
char* args[] = { cid, vaddr, paddr, size, 1 };   /* 1 = PAGE_DEV */
client_call(system_client, SYS_MAP, args);       /* paddr 想传什么就传什么 */
```

用户态可以把**内核代码段、页表、其它进程的页**映射进自己地址空间再改写 ⇒ 直接提权。
同理 `client_get(name)` 只要名字对就能拿到任何服务，无身份、无权限。

cap 模型把「我可不可以做」和「资源长什么样」拆开：

- 资源由**内核**持有并登记（设备窗口表、arena 对象、中断事件、服务、共享页）
- 进程手里只有**不可伪造的句柄**（slot + 代次），拿不到资源描述符就无法越权
- 句柄可**派生**（只能减权限）、可**传递**（带身份 badge）、可**撤销**（整棵子树）

代价是首次获取要一次 syscall；之后仍走共享页快路径，**不影响 11.2 的稳态延迟**。

### 5.2 cap 结构与句柄

```c
enum {
  CAP_MMIO,      /* 设备寄存器窗口 */
  CAP_DMA,       /* 物理连续内存（arena） */
  CAP_IRQ,       /* 中断事件 */
  CAP_SERVICE,   /* 调用某个服务的权利 */
  CAP_MEM,       /* 共享页（只读/只写/读写） */
};

enum {
  CAP_RIGHT_READ   = 1 << 0,
  CAP_RIGHT_WRITE  = 1 << 1,
  CAP_RIGHT_MAP    = 1 << 2,   /* 允许映射进自身地址空间 */
  CAP_RIGHT_GRANT  = 1 << 3,   /* 允许转授 */
  CAP_RIGHT_WAIT   = 1 << 4,   /* 允许在中断事件上等待 */
  CAP_RIGHT_SIGNAL = 1 << 5,   /* 允许转授中断事件 */
};

typedef struct cap {
  u16 type;
  u16 rights;
  u32 badge;        /* 授予时写入的身份标签 */
  u32 gen;          /* 代次，防 ABA */
  void* object;     /* window / arena / event / client / page */
  struct cap* parent;
  struct cap* child;    /* 派生树：父 → 子链表 */
  struct cap* sibling;  /* 同一父下的兄弟 */
} cap_t;

typedef u32 cap_handle;   /* (gen << 16) | slot，仅本进程有效 */
```

- 每进程一张 cap 表（挂在进程/VM 结构上），槽位上限 256
- 所有操作走 `ioctl(SYS_CAP_INVOKE, { handle, method, args })`，内核先校验 `slot + gen + rights`
- 句柄跨进程无效（代次与 slot 都属于本表），想给别人必须先 `SYS_CAP_TRANSFER`

### 5.3 MMIO 窗口 cap

内核维护设备窗口表（boot 时由平台初始化，或从 `/conf/foot.conf` 读）：

```c
/* 内核：设备名 → 窗口 + 中断，驱动不能自己编地址 */
static const foot_dev_t foot_devtab[] = {
  { "dwc2",   0x3F980000, 0x10000, IRQ_USB },
  { "v3d",    0x1002000000, 0x40000, IRQ_V3D_CSD },
  { "v3d-pm", 0x107D200000, 0x1000,  0 },
};
```

- 授予：服务启动时按配置拿到 `CAP_MMIO`，`rights = READ | WRITE | MAP`
- 映射：`cap_map(handle, vaddr)` 只能映射**该窗口范围内**的页，且强制 `PAGE_DEV`（无缓存）
- 用户态再也拿不到「任意物理地址映射」这个能力 —— 12.1 #1 从根上消失
- 台账：内核记录 `(pid, cap, vaddr, paddr, size)`，进程退出时自动 unmap

### 5.4 DMA arena cap

GPU、网卡、USB 控制器都需要**物理连续内存**，驱动还必须知道物理地址。

```c
/* 申请即得到一个 CAP_DMA，对象里带 va / pa / size */
cap_handle h = cap_alloc_arena(size, /*align=*/4096, /*flags=*/ARENA_NOCACHE);
foot_arena_t a;
cap_get_info(h, &a);        /* { va, pa, size, flags } */
```

- 内核侧：`phy_alloc_aligment(size, 4096)`（物理连续 + 恒等映射）
  或 `kmalloc_alignment(size, 4096, DEVICE_TYPE)`，再 `vmemory_map_type(..., PAGE_DEV)` 映射给请求方
- 用 `PAGE_DEV`（无缓存）可以省掉用户态无法执行的 `dc civac`，代价是 CPU 写带宽下降，
  与 EwokOS 的 `sys_dma` / `shm_contig` 同一取舍
- 共享给别的服务时用 `cap_derive(h, READ|MAP)` 派生只读子 cap（例如把渲染结果交给合成器）
- 用途：V3D 的 4MB 页表、QPU 代码、uniform 缓冲、渲染目标

### 5.5 中断事件 cap

用户态驱动不能装中断处理函数，内核把中断变成「事件对象」，用 cap 授权等待权。

```c
/* 内核：ISR 只做计数 + 唤醒，不做业务 */
irq_register(irq, foot_irq_isr, ev, "foot-irq", 0);
irq_enable(irq);

/* 驱动线程：睡在事件上（内部是 futex / 线程等待），超时返回 */
while (cap_irq_wait(ev_cap, timeout_us) == 0) {
    u32 seq = cap_event_seq(ev_cap);   /* 读序号，处理完再等下一次 */
    ...
}
```

- 对象：`foot_event_t { irq, seq, waiters }`；ISR 里 `seq++` + `thread_wait_notify_hook()`
- `rights`：`WAIT`（自己等）、`SIGNAL`（转授给别人，如输入子系统把事件转给桌面）
- 授予时校验：`irq` 必须属于该服务已获授权的设备窗口（防止任意中断注入）
- 现状对照：csudusb 用 `usleep(1000000)` 轮询（`foot/driver/csudusb/main.c:129`），
  USB 键鼠延迟 1 秒，就是「没有中断事件 cap」的直接后果

### 5.6 服务 cap 与共享页 cap

```c
cap_handle svc = cap_get_service("usbd");           /* 取代 client_get 直接拿共享页 */
cap_handle mem = cap_service_page(svc);             /* CAP_MEM，带方向 rights */
foot_call(svc, USB_GET_EVENT, &in, sizeof(in));     /* 内部走共享页快路径 */
```

- `CAP_SERVICE` 里带 `badge`（授予方写入的身份：uid / tid / 角色），服务端可 `cap_badge()` 读出
  ⇒ 服务端能判断调用者是谁、有没有权限调这个方法（12.1 #3 的解法）
- 共享页是两张 `CAP_MEM`：请求页给服务 `READ`，响应页给服务 `WRITE`；
  调用方方向相反 ⇒ **读写方向由页表权限强制，不靠约定**（12.1 #2 的解法）
- 快路径不变：cap 只在建立连接时解析一次，之后双方直读共享页，不进内核

### 5.7 派生、传递与撤销

| 操作 | 语义 | 实现要点 |
|---|---|---|
| `cap_derive(parent, rights)` | 生成子 cap，`rights ⊆ parent.rights` | 插入 CDT（`parent->child` 链表 + `sibling`）；不可提权 |
| `cap_transfer(handle, dst_tid)` | 把 cap 交给另一进程，可重写 badge | 目标是对方 cap 表的新 slot；源 cap 保留（除非同时 revoke） |
| `cap_revoke(handle)` | 递归销毁整棵子树 | DFS 子链表；对每个被销毁的 `CAP_MMIO/CAP_MEM` 执行 unmap |
| `cap_delete(handle)` | 只销毁自身 | 对象引用计数 `ref--`，归零时释放（页/arena 归还，窗口仅注销） |

撤销必须能「停下来」：正在被映射的 `CAP_MEM` 先标 `zombie`，等 unmap 完成再释放物理页。

### 5.8 授权形式与回收顺序

| 资源 | cap 类型 | 授权来源 | 回收时机 |
|---|---|---|---|
| MMIO 窗口 | `CAP_MMIO` | 设备窗口表（boot 配置） | 进程退出 / `cap_revoke` 时 unmap |
| DMA arena | `CAP_DMA` | `cap_alloc_arena` / 派生 | 最后一个 cap 销毁 |
| 中断 | `CAP_IRQ` | 随设备窗口一起授予 | 服务注销（先 `irq_disable`） |
| 服务 | `CAP_SERVICE` | `cap_get_service(name)` | 服务注销 / 进程退出 |
| 共享页 | `CAP_MEM` | 服务建立连接时创建 | 连接断开 |

**回收顺序**必须是「先停中断 → 再 unmap 内存 → 最后摘名字 / 释放对象」，
否则会出现「内存已释放但硬件还在写」。

## 六、故障隔离与恢复

### 6.1 调用超时

所有 `foot_wait` 必须带墙钟上限。超时语义：

- 服务方还在 = 请求可能仍会完成，客户端**不能重放**（设备状态已变）
- 服务方已死 = 内核负责把在飞请求标记为 `FOOT_EIO`，并唤醒所有等待者

### 6.2 服务崩溃检测

- 主路径：服务进程退出 → `close(/dev/foot)` → 内核 `service_close` 摘除名字并唤醒等待者
- 辅路径：心跳（每秒一次，3 次未到判定死亡），用于「进程活着但卡死」的情况

### 6.3 设备状态恢复责任的划分

| 场景 | 谁负责恢复 |
|---|---|
| 服务正常重启 | 服务自己重新 init 设备 |
| 服务崩溃、设备仍工作 | 新实例 init 时先 reset 设备（不能假设干净状态） |
| 设备挂死（GPU wedge、USB 掉线） | 内核模块提供「复位原语」，服务通过资源接口调用 |

所以内核里仍需要极少量与硬件相关的代码（复位、AXI 排空），这是混合内核的合理分工。

## 七、用户态驱动开发指南（以 csudusb 为例）

现状实录（`foot/driver/csudusb/main.c`）：

```c
sys = client_get("system");          /* 拿到资源服务 */
mmio_init();                         /* 5 次 SYS_MAP 映射 GPIO/DWC2/USB 窗口 */
usb_init();                          /* UsbInitialise + UsbCheckForChange */
while (1) {                          /* 事件循环：每秒轮询 */
  UsbCheckForChange();
  ...KeyboardPoll...
  usleep(1000000);
}
```

标准步骤（目标形态）：

1. **注册自己**：`client_regist("usbd")`，声明提供的方法（如 `USB_GET_EVENT`）
2. **申请资源（全部走 cap）**：`cap_map` 拿 MMIO 窗口；`cap_alloc_arena` 拿 DMA 缓冲；`cap_irq_wait` 等中断事件
3. **初始化设备**：写寄存器，跑硬件状态机
4. **事件循环**：`foot_wait_event(超时)` → 处理中断/请求 → `foot_reply(cid)`
5. **退出**：注销服务 → 停中断 → 释放 arena → 关 fd

清单（写在驱动里就少踩坑）：

- [ ] 不要用 `usleep(1000000)` 轮询，改成事件等待
- [ ] 热路径禁止 `printf`（串口是阻塞写，会拖死整个系统）
- [ ] 所有等待都要有超时
- [ ] 设备寄存器访问用 `volatile`，映射必须 `PAGE_DEV`（无缓存）
- [ ] 驱动自己崩溃后，下一个实例必须能处理「设备处于中间状态」

## 八、与当前实现的差距

### P0（正确性，会崩或会错）

| # | 问题 | 位置 | 修法 |
|---|---|---|---|
| 1 | `api->cid` 从不归零，`api_size` 恒为 1 ⇒ 第二次调用就覆盖最后一槽，无法并发 | `client.c:24-30`、`service.c:175` | 每次响应后清 `cid`；`api_size` 由服务声明（≥4） |

| 4 | `memmove(api->args, arg, 128)` 读越界（调用方常传小数组） | `client.c:39` | 改为 `foot_msg_t`，按 `len` 拷贝 |

## 十一、性能模型

### 11.1 三个参照实现

| | LRPC（Liedtke 1993） | seL4 fastpath（2009/2014） | foot（现状 / 目标） |
|---|---|---|---|
| 核心手法 | 用户态 TCB、共享参数栈、lazy scheduling、direct process switch、small address space | 单页消息（寄存器 + IPC buffer）、跳过 cap 遍历、跳过调度决策、call/reply 专用路径 | 共享物理页双映射、零拷贝、ring 队列、futex 唤醒 |
| 优化目标 | 同步小消息往返 | 同步小消息往返（可验证） | 大消息、批量、异步完成 |
| 陷入次数/往返 | 2（call + reply return） | 1~2（call fastpath + reply） | 目标 0（稳态）或 1（futex 唤醒） |
| 数据传递 | 寄存器 + 共享栈（同 VA） | 寄存器（≤ 4~8 个）+ 1 页 IPC buffer | 共享页（240B ~ 整帧），零拷贝 |

### 11.2 延迟预算

量级估算，误差 ±50%。依据：ARMv8 异常进入/退出成本、Cortex-A76 的 cache 层级
（L1 64KB / 私有 L2 512KB / DSU 共享 L3 2MB）、IPI 唤醒成本、以及上述论文的公开数据。
频率按 2.4GHz 折算（1 cycle ≈ 0.42ns）。

| 操作 | cycles | ns | 说明 |
|---|---|---|---|
| 空 syscall 往返 | 150~250 | 60~100 | 异常进入 + 保存/恢复通用寄存器 + 分发查表 |
| LRPC 一次调用 | 250~450 | 100~190 | 2 次陷入 + 直接切换 + 寄存器传参；原文在 486 上约 120 cycles，现代流水线更深 |
| seL4 call fastpath | 200~400 | 85~170 | 1 次陷入 + 无 cap 遍历 + 无调度决策；x86 原文约 300 cycles |
| futex wake → 对端被调度 | 400~800 | 170~340 | 1 次 syscall + 等待队列操作 + **IPI 到另一核** + 目标核调度入口 |
| 跨核 cache line 传递（DSU L3 命中） | 60~120 | 25~50 | 生产者写、消费者读同一行 |
| **foot 稳态快路径**（对端已 spin 在 `tail`） | **40~120** | 17~50 | 写 240B 到共享行 + `stlr` 推进 tail + 对端 `ldar` 看到，无陷入 |
| **foot 目标（futex 唤醒路径）** | **500~900** | 210~380 | ring 写入 + futex syscall + IPI + 调度 |
| **foot 当前实现**（`client.c:53-55`） | **~1.2 亿** | **50,000,000** | `usleep(500000)` 退避，比 seL4 fastpath 慢 **5 个数量级** |

### 11.3 关键差异

1. **陷入次数**：LRPC 2 次、seL4 1 次、foot 0 次（稳态）。foot 的理论优势成立的前提是
   **服务方在另一颗核上空转**，等于拿 1/4 的 CPU 换延迟。
2. **是否做调度决策**：LRPC 用 lazy scheduling 跳过完整调度器，seL4 fastpath 直接跳过。
   foot 的 0 陷入路径天然没有调度，但**唤醒路径**必须经过完整调度器 + IPI，
   这是它比 seL4 慢的主因（400~800 cycles 大部分花在 IPI 和目标核调度入口）。
3. **地址空间**：三者都不需要 TLB flush —— LRPC 靠 small address space，seL4 靠 ASID，
   foot 靠「双方各自映射同一物理页、从不切换页表」。
4. **数据规模**：LRPC/seL4 的 fastpath 都限制在小消息（寄存器/单页），传 1080p 帧要退到 slowpath
   （页映射或多次拷贝）。foot 传句柄、数据留在共享页，大消息场景有结构性优势。
5. **语义方向**：foot 的服务方是消费者、请求方是生产者，天然适合异步（提交后不等）；
   LRPC/seL4 的 call 语义强制同步。

### 11.4 按负载判断

| 负载 | 更优 | 原因 |
|---|---|---|
| 高频小消息同步 RPC（文件系统元数据等） | seL4 / LRPC | 200~400 cycles，且不需要服务方空转 |
| 大块数据（帧缓冲、顶点数组、纹理） | **foot** | 零拷贝 + 只传句柄；LRPC/seL4 要么拷贝要么建映射 |
| 批量提交（一帧 100 条 2D 命令） | **foot** | 一次提交带 100 条，RPC 次数从 100 降到 1 |
| 异步完成（GPU 乱序返回） | **foot** | `cid` 配对天然支持；LRPC/seL4 的 call 是同步的 |
| 硬实时（毫秒级截止） | seL4 | 有 WCET 保证；foot 的唤醒延迟有 IPI 抖动 |

对 1080p 桌面：一帧若有 100 次 2D 操作，即使每次 300 cycles（125ns），总开销也只有 12.5us，
占 16.7ms 预算的 0.07%。而当前的 50ms 轮询会让一帧变成 5 秒。所以：

> **要补的不是「把 300 cycles 降到 100」，而是「把 100 次 RPC 压成 1 次批量提交 +
> 把 50ms 轮询变成 2us 唤醒」。**

### 11.5 目标值（验收线）

| 指标 | 当前 | 目标 | 依据 |
|---|---|---|---|
| 空载唤醒往返（1KB 消息，跨核） | 50ms | **< 5us** | 500~900 cycles + 调度抖动 ≈ 1~3us |
| 稳态快路径（对端轮询） | 50ms | **< 200ns** | 40~120 cycles |
| 批量吞吐（64 条 2D 命令/提交） | N × 50ms | **单次提交 < 10us** | RPC 摊薄到 156ns/条 |
| 空闲 CPU 占用 | 0%（睡在 `usleep`） | **0%（睡在 futex）** | 不能靠 spin 省 CPU |
| 单服务最大并发请求 | 1（单槽） | **≥ 64（ring）** | `api_size` 从 1 改 64 |

### 11.6 设计结论

1. **不追 LRPC/seL4 的同步小消息路径**。它们已把这条线压到 200~400 cycles，foot 用共享页
   最多追平，还要付出「服务方空转」的代价。该抄的是它们的三个技巧：
   **跳过调度决策、小消息走寄存器、不 flush TLB** —— foot 在第三点上已天然具备。
2. **唤醒成本是主要瓶颈**，优化方向是「减少唤醒次数」而不是「加快单次唤醒」：
   批量提交 + 服务方批量处理 + 只在 ring 空/满时唤醒，可把唤醒开销摊薄到 1/64。
3. **保留按需 spin**：图形栈活跃期（连续帧）让服务方短时 spin（如 50us 后再睡），
   活跃期延迟 200ns、空闲期 0% CPU。这是 LRPC 的 lazy scheduling 思想在用户态的变体。

### 11.7 实测方法

用户态可直接读 `cntvct_el0`（需内核允许），在调用前后各取一次，把差值写进共享页的统计槽，
分三个口径：

| 口径 | 起点 → 终点 | 对应 11.2 的哪一行 |
|---|---|---|
| `submit` | 开始写消息 → tail 推进完成 | foot 稳态快路径 |
| `wake` | tail 推进 → 服务方读到并开始处理 | futex 唤醒路径 |
| `complete` | 提交 → 收到同 `cid` 的响应 | 端到端往返 |

注意：**测量时必须先关掉热路径日志**（`printf` 一次是毫秒级，测出来的是串口不是 IPC），
且要关中断或至少多次取中位数，避免 IPI/时钟中断抖动污染样本。

## 十二、设计缺点与改进

第八章列的是「实现 bug」，本节列的是**结构性缺点**——即使把 P0 全修完，这些仍然存在。
每条给「缺点 → 影响 → 改进」，最后列出**明确不修**的取舍。

### 12.1 安全与隔离

| # | 缺点 | 影响 | 改进 |
|---|---|---|---|
| 1 | `SYS_THREAD_MAP` 接受任意 `phy_addr`，不校验范围（`sysfn_thread.c:80-104`） | 用户态可以把**内核内存、页表、其它进程的页**映射进自己的地址空间 | 由 cap 模型解决（见 5.3）：用户态只持有 `CAP_MMIO` 句柄，`cap_map` 只能映射该设备窗口；`sys_thread_map` 降级为内核内部实现，不再对用户态开放物理地址 |
| 2 | 共享页无方向约束，请求区与响应区重叠 | 服务端可改写请求、客户端可改写响应，出错时无法判断谁写坏 | 用两张 `CAP_MEM` 分别授予读/写权限（见 5.6），方向由页表权限强制，而不是靠约定 |
| 3 | 任何进程都能 `client_get` 任意服务并调任意方法 | 无权限模型，一个服务被攻破等于全部 | 由 `CAP_SERVICE` + badge 解决（见 5.6）：服务端按 badge 鉴权，cap 只携带已授权的方法位图 |

### 12.2 数据通路

| # | 缺点 | 影响 | 改进 |
|---|---|---|---|
| 4 | 无背压 / 流控 | ring 满时行为未定义（当前是覆盖最后一槽），请求静默丢失 | 满时返回 `EAGAIN`，生产者 `FUTEX_WAIT` 在 `head` 上；单独统计「丢弃次数」 |
| 5 | 单一 FIFO，无优先级 | 输入事件（要求 < 1ms）会被日志/后台任务阻塞 | 每优先级一条 ring（或 per-client 队列），唤醒时按优先级出队 |
| 6 | 服务端完全串行（`client_run` 单线程跑所有方法） | 一个慢方法（如 100ms 的模糊）卡住整个服务的输入响应 | 慢操作异步化：立即返回 `cid`，完成后投递响应；`client_run` 只做轻量派发 |
| 7 | 参数上限 128 字节且定长拷贝（`client.c:39`） | 大参数只能另开共享页，协议分裂；小参数读越界 | `foot_msg_t{len,payload[240]}`，按 `len` 拷贝；大对象一律传句柄 |

### 12.3 生命周期与资源回收

| # | 缺点 | 影响 | 改进 |
|---|---|---|---|
| 5 | 注销时不回收共享页（`service.c:107` 只摘名字） | 每个注册过的服务泄漏一页，长期运行会耗尽 | `client_t` 记录共享页 `(va, pa, size)`，注销时 `sys_munmap` + 内核台账扣除 |
| 6 | 无代次（generation） | 服务重启后 `id` 复用，客户端缓存的旧 id 连到新服务（协议不匹配） | `id = (generation << 16 | slot)`；`client_get` 返回代次，调用时校验 |
| 7 | 无配额 | 一个服务可注册多个名字把 `clients[]`（100）打满 | per-服务 名字数与共享页数上限；超限返回错误 |
| 8 | 无心跳 | 「进程活着但卡死」检测不出来，客户端只会等到超时 | 服务每 N ms 更新一次心跳时间戳，内核/客户端 3 次未更新判定死亡 |

### 12.4 可观测性

| # | 缺点 | 影响 | 改进 |
|---|---|---|---|
| 9 | 只有 `printf` | 无法回答「延迟多少、失败率多少、谁在拖慢」 | 每 client 一组计数器（请求数/超时/失败/最近 P50）；`/dev/foot/<name>` 可 `read` 出统计 |
| 10 | 无故障注入 | 崩溃、超时、ring 满这些路径几乎测不到 | debug 模式支持「第 N 次调用注入超时/注入崩溃」，并纳入回归脚本 |

### 12.5 明确不做的取舍

| 不做 | 理由 |
|---|---|
| LRPC 式 direct process switch | 收益（省 200~400 cycles）远小于复杂度（需要内核线程切换原语、优先级反转处理），且图形负载不缺这几百 cycles（见 11.4） |
| 内核内消息语义校验 | 内核一旦理解消息内容，新增方法就要改内核，违背「内核只做路由」的初衷；`client_t` / `api_t` 在两侧各存一份定义是刻意的（内核与用户态库解耦，任一侧可独立演进），变更时两侧同批修改 |
| 每条消息 CRC | 成本（每帧几十条）大于收益；用「方向分离 + 长度校验」覆盖绝大多数误用 |
| 内核态驱动兜底 | 会把混合内核退化成宏内核；设备复位这类必须特权的操作以**资源接口**形式暴露即可（见 6.3） |
