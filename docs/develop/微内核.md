# 微内核（foot 服务框架）

YiYiYa 提供微服务级别的支持：一个服务可以是一个程序、一个 so、一个设备驱动、一个函数。
可以开多个服务、负载均衡，也可以多个版本同时开。内核除了调度 CPU，也负责服务的资源仲裁。

> 本文是设计文档，描述 **foot**（原 gaga）服务框架的目标模型、当前实现与迁移路径。
> 代码：内核 `duck/modules/foot/`、用户态库 `eggs/libfoot/`、服务与驱动 `foot/service/`、`foot/driver/`。

---

## 一、设计初衷

传统微内核的服务调用要走两次 IPC（A→内核→B，返回再一次），每次都是一次陷入。
foot 的思路是把**参数与返回值放在共享内存里**，双方各自在自己的地址空间直接读写同一块物理页：

```
a 调 b：写共享页 → b 在自己的线程里取到 → 直接执行 → 写回结果
```

- 内核只负责「建共享页 + 通知有消息」，不参与每次的数据搬运 ⇒ 没有数据拷贝开销
- 同一物理页可以映射给多个服务 ⇒ 支持一个请求多个订阅者（广播）、多实例负载
- 服务注册后按名字查找 ⇒ 应用不需要知道服务在哪个进程

这仍然是 IPC（不是真的函数调用），但数据零拷贝、且可以把「提交」与「完成」解耦成异步队列，
这一点对图形/GPU 这类「一帧几十次小请求」的场景尤其重要。

## 二、总体架构

```
┌──────────────────────────────────────────────────────────┐
│ 应用 / 桌面（x11、weston、app/*）                          │
└───────────────┬──────────────────────────────────────────┘
                │ libfoot: client_regist / client_get / client_call
┌───────────────▼──────────────────────────────────────────┐
│ 服务与驱动（foot/service、foot/driver/*）                  │
│   systemd（资源服务）  vfsd  servicea/b                   │
│   csudusb（USB 主机栈）  wifi  bluetooth  tinyusb          │
└───────────────┬──────────────────────────────────────────┘
                │ ioctl(/dev/foot) + 共享页
┌───────────────▼──────────────────────────────────────────┐
│ 内核 foot 模块（duck/modules/foot/）                       │
│   · 客户端表 clients[]（名字 / id / tid / 状态）           │
│   · 共享页分配与跨进程映射（service_map_client_api）        │
│   · 资源仲裁：MMIO 窗口、DMA arena、中断事件（规划）        │
└──────────────────────────────────────────────────────────┘
```

分层原则：**内核只做「登记 / 授权 / 建共享页 / 唤醒」，不解释消息内容**。
消息语义由服务自己定义，新增服务不需要改内核。

## 三、调用模型

### 3.1 当前实现（共享页 + 槽数组状态机 + futex 唤醒）

共享结构（`duck/modules/foot/service.h`，与 `eggs/libfoot/client.h` 逐字段一致）：

```c
#define MAX_API_SLOTS 64   /* 每 client 最多 64 个并发请求槽 */
#define MAX_ARGS_BUF  240  /* 单请求 payload 上限（字节） */
#define FOOT_CTL_WORDS 4   /* 槽数组之后预留 4 个字：kick + 保留 */

typedef struct api {
  int cid;                  /* 0=空闲；非 0=正在处理（值即 seq） */
  int state;                /* API_INIT/REDAY/RETURN/FINISH */
  int err;                  /* 响应错误码 */
  unsigned int seq;         /* 请求序号（识别陈旧响应） */
  unsigned int claim_ms;    /* 调用方提交时刻，服务端据此回收僵尸槽 */
  unsigned int len;         /* args 有效长度 */
  unsigned int flags;       /* 保留 */
  void* fn;                 /* 方法号 */
  void* ret;                /* 返回值（只能是值，不能跨进程传指针） */
  char args[MAX_ARGS_BUF];  /* payload，按 len 拷贝 */
} api_t;
```

一个 client 的共享区 = `api_size` 个槽 + 4 个控制字，页数按字节数向上取整（多页）。

建立过程（`duck/modules/foot/service.c`）：

1. 服务方 `client_regist_ex(name, slots)` → ioctl(SYS_NEW_CLIENT) → 内核分配 `client_t`，
   `sys_mmap2(NULL, pages*PAGE_SIZE, MAP_ANON)` 建共享区，槽位数按声明（上限 64）
2. 调用方 `client_get(name)` → 内核 `page_v2p(服务方页表, apis+i*PAGE)` 拿物理页，
   在调用方页表里 `page_map_on(..., PAGE_USER)` 逐页映射成调用方 VA（两边 VA 不同，物理页相同）
3. 之后双方读写同一批物理页，`state` 做门闩、`cid`/`seq` 做配对

调用方（`eggs/libfoot/client.c` 的 `client_call_ex`）：

- 找 `cid==0` 的槽（无则返回 `-2`）→ 按 `len` 拷贝 payload → CAS `cid:0→seq` → `state=API_REDAY`
- `kick++` 后 `FUTEX_WAKE(kick,1)` 唤醒可能在睡的服务端
- `FUTEX_WAIT(&state, 当前值, 剩余超时)` 睡眠等结果；服务端发布后 `FUTEX_WAKE(&state,1)`
- 超时返回 `-1`：能撤销就 CAS 回 `API_INIT`，否则清 `cid` 让服务端丢弃迟到结果

服务方（`client_run` / `client_run_ex`）：

- **先读 `kick` 再扫槽**：扫槽期间到达的提交会改 `kick`，随后的 `FUTEX_WAIT` 因值不匹配立即返回，不会睡死
- 有 `API_REDAY` 的槽就执行 handler（`client_run_ex` 额外拿到 `len`）→ 校验 `cid` 未变 → 写 `ret` →
  CAS `REDAY→RETURN` → `FUTEX_WAKE(&state,1)`
- 全部空闲时 `FUTEX_WAIT(kick, k, 500ms)`；500ms 是兜底上限（保证 `client->state` 退出条件能及时生效），
  不是轮询——正常路径由调用方的 `FUTEX_WAKE` 唤醒

**所有状态迁移一律 CAS**：调用方与服务方是并发进程，"看到的状态"到"写回去"之间槽位可能已被
取走结果甚至放进新请求；直接 `store` 会静默抹掉新请求（实测 32 次连续调用从第 3 次开始超时）。

**futex 字的身份 = 物理页 + 页内偏移，且物理页在唤醒时按各自页表现算**：只比裸 VA 的话，
共享页在两个进程里 VA 不同 ⇒ 永远唤不醒（foot 每次调用退化成睡满超时，9.6s → 92s）；
只按登记时的物理地址比又会踩 COW（整页搬家后登记值失效）。详见 `sysfn_thread.c` 的 `futex_match`。

### 3.2 目标模型：快路径 + 慢路径

| 路径 | 条件 | 行为 |
|---|---|---|
| **快路径** | 共享 ring 有空位、服务方 alive | 写消息 + 原子推进 `tail`，**不陷内核** |
| **慢路径** | ring 满 / 需要阻塞等结果 | `SYS_FUTEX` 睡在 ring 的某个地址上，服务方 `FUTEX_WAKE` |

要点：

1. **环形队列代替定长槽**：`foot_msg_t` 数组 + `head/tail`（单生产者单消费者用两个原子变量即可，
   多生产者需要 CAS 或一个 ticket 锁）。
2. **请求/响应按 `cid` 配对**：调用方分配 `cid`（单调递增），响应里带回同一个 `cid`，
   这样支持**乱序完成**（GPU 天然乱序）。
3. **不阻塞的提交**：`foot_submit()` 只入队并返回 `cid`；`foot_wait(cid, timeout)` 才等结果。
   图形栈一帧可以攒 N 条命令一次提交（批量）。
4. **超时**：每个等待都带墙钟上限，超时返回 `FOOT_ETIMEDOUT`，**不允许无超时死等**。

**落地情况（2026-10-31）**

| 条目 | 状态 | 落地方式 |
|---|---|---|
| cid/seq 配对、乱序完成 | ✅ | `api_t.seq` 单调递增，服务端发布前校验 `cid` 未变 |
| len 定长 payload | ✅ | `api_t.len` + `MAX_ARGS_BUF=240`，按 `len` 拷贝 |
| 每次等待带超时 | ✅ | `client_call_ex(..., timeout_ms)`，超时 `-1` 且回收槽位 |
| 并发槽位 ≥64 | ✅ | `MAX_API_SLOTS=64`，共享区多页映射 |
| futex 快/慢路径 | ✅ | 提交/响应 + `kick` 字唤醒；空闲无轮询 |
| 非阻塞 `submit`/`wait` 分离 | ✅ | `client_submit_ex`（只入槽即返回 `foot_ticket_t{slot,seq}`）+ `client_wait_ex`；`client_call_ex` = submit + wait |
| 票据防串号 | ✅ | `wait` 先校验 `api->seq == ticket.seq && cid != 0`，槽位被回收复用时旧票据返回 `-1` |
| 环形队列 `foot_msg_t` | ❌ | 现在用"槽数组 + seq"实现同一语义（乱序完成、无丢请求）；ring 只对"批量提交"有额外价值 |

消息格式（建议，ring 版本如果要做再落地）：

```c
#define FOOT_MSG_MAX 240
typedef struct {
  u32 cid;        /* 请求 id，响应原样带回 */
  u32 type;       /* 方法号 */
  u32 flags;      /* 同步/异步、是否需要唤醒 */
  u32 status;     /* 响应：0=OK 或 errno */
  u32 len;        /* payload 有效长度 */
  u8  payload[FOOT_MSG_MAX];
} foot_msg_t;
```

大对象（画布、显存、DMA 缓冲）不放进 payload，只放**句柄**（BO id / arena id / 共享页 id），
由资源接口（第五节）单独授权。

### 3.3 并发约束

- 一个服务默认单线程处理请求（`client_run` 串行），**但可以多实例**（`client_regist` 多次同名 = 多个服务线程）
- 服务内部若需要并发，自己起线程，foot 不限制
- 内核 `clients[]` 最多 `MAX_CLIENTS=100`（`service.h:32`），槽位生命周期必须可靠回收

## 四、服务注册与发现

| 接口 | 语义 | 实现位置 |
|---|---|---|
| `client_regist(name)` | 注册服务（可同名多次 = 多实例） | `client.c:122` → `service.c:174` |
| `client_get(name)` | 按名字拿第一个存活实例 | `client.c:146` → `service.c:162` |
| `client_id(id)` | 按 id 拿服务 | `client.c:169` → `service.c:195` |
| `client_run(client, fn)` | 进入服务循环（阻塞） | `client.c:69` |
| `clirent_un_regist(client)` | 注销 | `client.c:192` |

设计要求：

1. **代次（generation）**：`id` 会被回收复用，客户端缓存 id 时必须带 generation，
   否则服务重启后旧 id 会连到新服务上（协议版本不匹配的经典事故）。
2. **健康状态**：`service_get_client_name` 已经用 `thread->state != THREAD_STOPPED` 过滤死亡实例
   （`service.c:27-36`），但**实例数组没有上限检查**，必须补。
3. **注销必须可重入**：等所有在飞请求完成或超时后再摘除名字，否则客户端拿到已释放的共享页。
4. **服务声明**：服务在注册时声明自己支持的方法号与所需资源（可选，用于客户端发现能力）。

## 五、资源授权（capability 模型）

用户态驱动要能工作，只需要三样东西：**MMIO 窗口、DMA arena、中断事件**。目前只齐了第一样。
而这三样（以及服务本身）都必须用 **capability（能力句柄）** 授权，不能让用户态自己指定资源。

> 本章按 **v2 设计**书写：内核对象 + 类型注册表 + **TCB 级 CSpace** + 通用/类型权限位 + 8 个原语。
> 5.2 末尾有 v1（已实现）与 v2（目标）的逐项对照 —— v1 是“设备窗口白名单 + 派生树”，
> 只覆盖 `OBJ_DEVWIN` 一种对象，没有 epoch、没有 invoke 分派。

### 5.1 为什么必须用 cap

现状的 `sys_thread_map(tid, virt, phys, size, attr)` 直接吃用户态给的 `phys`，不校验范围：

```c
char* args[] = { cid, vaddr, paddr, size, 1 };   /* 1 = PAGE_DEV */
client_call(system_client, SYS_MAP, args);       /* paddr 想传什么就传什么 */
```

用户态可以把**内核代码段、页表、其它进程的页**映射进自己地址空间再改写 ⇒ 直接提权。
同理 `client_get(name)` 只要名字对就能拿到任何服务，无身份、无权限。

cap 模型把「我可不可以做」和「资源长什么样」拆开：

- 资源由**内核**持有并登记（设备窗口表、arena 对象、中断事件、服务、共享页）
- 进程手里只有**不可伪造的句柄**（slot + 代次），拿不到资源描述符就无法越权
- 句柄可**派生**（只能减权限）、可**传递**（带身份 badge）、可**撤销**（整棵子树）

代价是首次获取要一次 syscall；之后仍走共享页快路径，**不影响 11.2 的稳态延迟**。

### 5.2 核心抽象：内核对象 · CSpace · 句柄（v2 设计）

v1 只做了“句柄 + 权限位 + 派生树 + 设备窗口白名单”，没有对象层、类型注册表、epoch
和统一的 invoke 原语 —— 那是设备白名单，不是 capability 系统。v2 按下面的三层重做：

```
用户线程 ──handle──> CSpace（TCB 内的槽位数组）──真实 cap──> 内核对象
```

#### 5.2.1 内核对象

一切资源都是内核对象，统一三件套：类型、全局 id、生命周期版本号。

```c
typedef u16 obj_type_t;
enum {
  OBJ_UNTYPED,   /* 一段物理内存，可 retype 成其它对象 */
  OBJ_FRAME,     /* 物理页，可 MAP 到地址空间 */
  OBJ_ARENA,     /* 物理连续内存（DMA / 渲染目标），带 pa 与对齐 */
  OBJ_DEVWIN,    /* 设备寄存器窗口 */
  OBJ_IRQ,       /* 中断事件 */
  OBJ_ENDPOINT,  /* IPC 端点（请求/响应队列） */
  OBJ_TCB,       /* 线程控制块的引用 */
  OBJ_TYPE_MAX
};

typedef struct kobject {
  obj_type_t ty;
  u64 id;      /* 全局唯一对象 id */
  u64 epoch;   /* 生命周期版本号：销毁时 +1 */
  void* state; /* 具体对象数据，由类型 ops 解释 */
  u32 refs;    /* 存活的能力数，归零才 destroy() */
} kobject_t;
```

`epoch` 是防 use-after-free 的关键：能力里保存创建时的 epoch，解析时与对象头比对，
不符即 `CAP_STALE`。这样“对象已回收但句柄还在”不再需要靠“先 unmap 再释放”的时序去赌。

#### 5.2.2 类型注册表

```c
typedef struct obj_ops {
  obj_type_t ty;
  const char* name;
  int  (*invoke)(kobject_t* obj, cap_t* cap, struct foot_msg* m);
  void (*destroy)(kobject_t* obj);                    /* 最后一个能力消失 */
  int  (*map)(kobject_t* obj, void* pgdir, vaddr_t va, u32 off, u32 len);
  void (*unmap)(kobject_t* obj, void* pgdir, vaddr_t va, u32 len);
} obj_ops_t;

int obj_register(const obj_ops_t* ops); /* boot 期注册，返回 ObjTypeId */
```

新增一种资源（GPU 上下文、I2C 通道、定时器）只需 `obj_register` + 一组类型权限位，
cap 核心的查找 / 校验 / 派生 / 撤销逻辑**一行不改** —— 这是“通用”的落点。

#### 5.2.3 CSpace 与句柄（挂在 TCB 上）

```c
typedef struct cap {
  kobject_t* obj;  /* 对象引用 */
  obj_type_t ty;   /* 冗余存储，快速类型校验 */
  u32 rights;      /* 通用位 | 类型位（见 5.3） */
  u64 epoch;       /* 从对象头复制 */
  u32 parent;      /* 派生链：父槽句柄，0 = 根 */
  u32 slot;        /* 自身槽号（递归销毁时清槽，防 double free） */
} cap_t;

typedef struct cspace {
  cap_t* slots;   /* 动态数组：64 起，上限 4096 */
  u32 nslot;
  u32* gens;      /* 每槽代次，防 ABA */
  u32 ref;        /* 共享这张表的 TCB 数（CLONE_VM） */
} cspace_t;

typedef u32 cap_handle;  /* (gen << 12) | slot：slot 12 位 = 4096 槽，gen 20 位 */
```

- **每 TCB 一个 `cspace_t*`**（`thread_t.cspace`），不是每进程一张表
- 解析 O(1)：数组下标 + gen 比较，热路径不遍历、不加锁
- 句柄只在所属 CSpace 内有意义；跨线程/进程传递必须走 IPC grant（5.7），内核做一次翻译
- gen 回绕时该槽强制失效并重新分配，避免长时间运行后 ABA 命中

#### 5.2.4 统一调用入口

```c
int cap_invoke(u32 handle, struct foot_msg* m) {
  cap_t* c = cspace_lookup(cur_thread()->cspace, handle);
  if (!c)                                return -CAP_NIL;
  const obj_ops_t* ops = obj_ops_get(c->ty);
  if (!ops)                              return -CAP_TYPE;
  if (!(c->rights & RIGHT_INVOKE))       return -CAP_RIGHTS;
  if (!c->obj || c->obj->epoch != c->epoch) return -CAP_STALE;
  return ops->invoke(c->obj, c, m);      /* 类型相关分派 */
}
```

热路径成本 = 两次数组访问 + 两次比较 + 一次间接调用；常用能力可再加一层
“线程内能力缓存”（`(handle, cap*)` 的 4 项直接映射缓存），退化成一次指针比较。

#### 5.2.5 权限位

通用权限（低 16 位，所有类型语义一致）：

```c
enum {
  RIGHT_LOAD    = 1 << 0,  /* 读对象状态/数据 */
  RIGHT_STORE   = 1 << 1,  /* 改对象状态/数据 */
  RIGHT_INVOKE  = 1 << 2,  /* 调用对象方法 */
  RIGHT_GRANT   = 1 << 3,  /* 复制给其它 CSpace */
  RIGHT_MINT    = 1 << 4,  /* 派生受限能力 */
  RIGHT_REVOKE  = 1 << 5,  /* 撤销自己派生出的能力 */
  RIGHT_DESTROY = 1 << 6,  /* 销毁对象 */
  RIGHT_CREATE  = 1 << 7,  /* 基于该对象创建子对象 */
};
```

类型位（高 16 位，按对象类型解释；不同类型可以复用同一位）：

| 类型 | 类型位 |
|---|---|
| `OBJ_FRAME` | `MAP`(1<<16)、`UNMAP`(1<<17) |
| `OBJ_ENDPOINT` | `SEND`、`RECV`、`NOTIFY` |
| `OBJ_IRQ` | `ACK`、`BIND` |
| `OBJ_DEVWIN` | `MAP`、`MAILBOX`（直接读写寄存器） |
| `OBJ_TCB` | `READ_REGS`、`WRITE_REGS`、`SUSPEND`、`RESUME` |

规则：

- **单调不增**：`mint` 执行 `new = src.rights & desired`，任何路径都不能造出权限更大的能力
- 类型位与通用位同在一个 `u32`，但校验时先按 `ty` 选语义，不做“位名全局唯一”的假设
- `GRANT`（复制到别的 CSpace）与 `MINT`（本 CSpace 内派生）分开：只给服务转授资格时只给 `GRANT`，不给 `MINT`

**v1 → v2 对照**

| 设计项 | v1（已实现，2026-10-31） | v2（目标） |
|---|---|---|
| 对象 | 无，`cap_t.object` 直指静态窗口表 | `kobject_t` + 类型注册表 + epoch |
| 表归属 | `vmemory_t.caps`（地址空间） | `thread_t.cspace`（TCB），`ref` 计数共享 |
| 槽位 | 固定 64 | 动态 64→4096 |
| 句柄 | `(gen<<8)｜slot` | `(gen<<12)｜slot` |
| 权限 | READ/WRITE/MAP/GRANT/WAIT/SIGNAL | 通用 8 位 + 类型位（5.3） |
| 原语 | get_mmio / derive / revoke / map | retype / copy / move / mint / revoke / delete / invoke / info |
| 授权判定 | 按名字申请 + **euid 校验** | **不查身份**：boot 授权表 + mint 派生 + policy server |
| 设备映射 | `cap_map` 内联 MMIO 分支 | `OBJ_DEVWIN.map` / `OBJ_FRAME.map` 走 ops |

### 5.3 MMIO 窗口对象（`OBJ_DEVWIN`）

内核维护设备窗口表（boot 时由平台初始化，或从 `/conf/foot.conf` 读）：

```c
/* 内核：设备名 → 窗口 + 中断，驱动不能自己编地址 */
static const foot_dev_t foot_devtab[] = {
  { "dwc2",   0x3F980000, 0x10000, IRQ_USB },
  { "v3d",    0x1002000000, 0x40000, IRQ_V3D_CSD },
  { "v3d-pm", 0x107D200000, 0x1000,  0 },
};
```

- 授予：**boot 授权表**（`/conf/foot.conf`）把窗口对象登记给指定任务；其它任务只能从持有者
  `mint` 出受限能力（`MAP|MAILBOX|LOAD|STORE`）。内核**不查 uid** —— “谁是 root”
  不是万能钥匙（见 5.9）
- 映射：`invoke(cap, DEVWIN_MAP, {vaddr, offset, len})` → `OBJ_DEVWIN.map`，只能落在
  窗口范围内，且强制 `PAGE_DEV`（无缓存）
- 用户态再也拿不到「任意物理地址映射」这个能力 —— 12.1 #1 从根上消失
- 台账：`(cspace, cap, vaddr, paddr, len)`，CSpace 最后一个引用释放时自动 unmap

### 5.4 DMA arena 对象（`OBJ_ARENA`）

GPU、网卡、USB 控制器都需要**物理连续内存**，驱动还必须知道物理地址。

```c
/* 从 untyped 切出物理连续 arena，对象里带 pa / size / flags */
cap_handle h = cap_retype(untyped_cap, OBJ_ARENA, RIGHT_LOAD | FRAME_MAP);
foot_arena_t a;
cap_info(h, &a);            /* { pa, size, flags } */
```

- 内核侧：`phy_alloc_aligment(size, 4096)`（物理连续 + 恒等映射）
  或 `kmalloc_alignment(size, 4096, DEVICE_TYPE)`，再 `vmemory_map_type(..., PAGE_DEV)` 映射给请求方
- 用 `PAGE_DEV`（无缓存）可以省掉用户态无法执行的 `dc civac`，代价是 CPU 写带宽下降，
  与 EwokOS 的 `sys_dma` / `shm_contig` 同一取舍
- **第三条路（渲染目标推荐）**：`ARENA_CACHEABLE` + 内核代做缓存维护。用户态在 EL0 不能执行
  `dc civac`，所以提供 `cap_cache_maint(handle, va, len, op)`（clean / invalidate / clean+invalidate），
  单次约 200 cycles。1080p 渲染目标每帧一次 clean 即可，换来可缓存写的带宽。
  这类 arena **默认禁止 CPU 直写**，必须配 `cap_cache_maint`，避免「以为一致其实不一致」
- 共享给别的服务时用 `cap_mint(h, READ|MAP)` 派生只读子 cap（例如把渲染结果交给合成器）
- 用途：V3D 的 4MB 页表、QPU 代码、uniform 缓冲、渲染目标

### 5.5 中断事件对象（`OBJ_IRQ`）

用户态驱动不能装中断处理函数，内核把中断变成「事件对象」，用 cap 授权等待权。

```c
/* 内核：ISR 只做计数 + 唤醒，不做业务 */
irq_register(irq, foot_irq_isr, ev, "foot-irq", 0);
irq_enable(irq);

/* 驱动线程：睡在事件上（内部是线程等待），超时返回 */
while (cap_invoke(ev_cap, IRQ_WAIT, &(struct irq_wait){.timeout_us = 1000}) == 0) {
    u32 seq = cap_invoke(ev_cap, IRQ_SEQ, NULL);  /* 读序号，处理完再等下一次 */
    ...
}
```

- 对象：`foot_event_t { irq, seq, waiters }`；ISR 里 `seq++` + `thread_wait_notify_hook()`
- 类型位：`IRQ_ACK`（确认/复位）、`IRQ_BIND`（绑定到等待者）；通用位 `LOAD`（读 seq）、
  `WAIT` 语义由 `IRQ_BIND` + `INVOKE` 组合表达
- 授予时校验：`irq` 必须属于该服务已获授权的设备窗口（防止任意中断注入）
- **共享中断**（GPIO bank、PCIe 共享线）无法用「属于某窗口」判断：允许 `OBJ_IRQ` 订阅
  「共享 IRQ 组」，ISR 只递增组内各订阅者的 `seq`，由各驱动自己判断是不是自己的中断
- 现状对照：csudusb 用 `usleep(1000000)` 轮询（`foot/driver/csudusb/main.c:129`），
  USB 键鼠延迟 1 秒，就是「没有中断事件 cap」的直接后果

### 5.6 服务端点与共享页对象（`OBJ_ENDPOINT` / `OBJ_FRAME`）

```c
/* 端点能力由 boot 授权表装进 CSpace（或由父任务 mint），不再是"名字一查就有" */
cap_handle svc = boot_endpoint("usbd");
cap_handle req = frame_of(svc, REQ);   /* OBJ_FRAME：客户端只写、服务端只读 */
cap_invoke(svc, EP_CALL, &msg);        /* 内部走共享页快路径 */
```

- `OBJ_ENDPOINT` 能力带 `badge`（mint 时写入的 tid / 角色），服务端用 `cap_info()` 读出
  ⇒ 服务端能判断调用者是谁、有没有权限调这个方法（12.1 #3 的解法）；badge 只做审计，
  **内核对它的信任度为零**，越权与否由“有没有端点能力”决定
- 共享页是两张 `OBJ_FRAME`：请求页给服务 `READ`，响应页给服务 `WRITE`；
  调用方方向相反 ⇒ **读写方向由页表权限强制，不靠约定**（12.1 #2 的解法）
- 快路径不变：cap 只在建立连接时解析一次，之后双方直读共享页，不进内核

### 5.7 原语：retype / copy / move / mint / revoke / delete / invoke

所有操作第一个参数永远是句柄，全部是系统调用（自定义号段 600+）：

| 号 | 原语 | 语义 | 实现要点 |
|---|---|---|---|
| 600 | `cap_retype(untyped_h, ty, rights)` | 从 Untyped 切出对象并返回能力 | 推进 untyped 的空闲偏移；对象登记进对象表 |
| 601 | `cap_copy(src_h, dst_cspace, dst_slot)` | 复制能力到另一个 CSpace | 需 `GRANT`；目标 CSpace 可写；`obj->refs++` |
| 602 | `cap_move(src_h, dst_cspace, dst_slot)` | 移动能力 | 源槽清空（gen++），`obj->refs` 不变 |
| 603 | `cap_mint(src_h, rights)` | 派生受限能力 | `new = src & desired`；记 `parent`；需 `MINT` |
| 604 | `cap_revoke(h)` | 撤销该能力派生出的所有能力 | 见下 |
| 605 | `cap_delete(h)` | 只删自身 | 清槽；`obj->refs--`，归零 → `ops->destroy` + `epoch++` |
| 606 | `cap_invoke(h, msg)` | 调对象方法 | 5.2.4 的入口 |
| 607 | `cap_info(h)` | 查 `{ty, rights, obj_id, epoch}` | 只读，不要求 `INVOKE` |

IPC 携带能力（`cap_send` 的 msg 里带一个句柄）走“内核翻译”：发送方能力 `copy` 到接收方
CSpace 的新槽，返回的新句柄回写给接收方；`refs` 相应增减。数据通路照旧零拷贝，但**授权
生命周期仍然经过内核**。

#### 撤销：用「父槽号 + 线性扫描」而不是 child 链表

v1 用 `parent/child/sibling` 三指针维护派生树、撤销时 DFS。实测踩到的坑：递归销毁子能力后
忘了清它的槽位，之后 `cap_table_destroy` 再遍历一次就是 double free
（`ya_free bad state ... size=40`）。指针树和槽数组两套结构必须手工保持一致，很容易漏。

v2 只存父槽号，撤销时扫描自己的表：

```c
static int descends_from(cspace_t* cs, u32 slot, u32 root) {
  u32 p = slot;
  while (p != 0) {                 /* 0 = 根，最多走到根就停 */
    if (p == root) return 1;
    p = cs->slots[p].parent;
  }
  return 0;
}

void cap_revoke(cspace_t* cs, u32 handle) {
  u32 root = handle & SLOT_MASK;
  for (u32 i = 1; i < cs->nslot; i++) {
    if (cs->slots[i].obj == NULL) continue;
    if (descends_from(cs, i, root)) cap_delete_slot(cs, i);  /* 含 unmap + refs-- */
  }
}
```

- 单表 ≤ 4096 槽，一次扫描约 16KB，微秒级；比维护 child 链表简单，也不会断链/漏清槽
- 派生链实际很短（根 → 服务 → 客户端，通常 1~3 层），向上走是常数级
- `fork` 复制 CSpace 时 `parent` 需要在子表里按原槽号重新指向

撤销必须能「停下来」：正在被映射的 Frame 能力先标 `zombie`，等 unmap 完成再释放物理页。

**但硬件不认 zombie**：撤销 `OBJ_ARENA` 时 V3D 可能正在往那块内存写。所以撤销必须串成链：

```
revoke(OBJ_ARENA)
  → 找出使用该 arena 的设备（同服务的 OBJ_DEVWIN / OBJ_IRQ）
  → 先停设备（走「复位原语」cap，见 6.3）
  → 等该设备的完成中断或超时
  → 再 unmap、再归还物理页
```

结论：**`OBJ_ARENA` 不能独立撤销** —— 要么拒绝（返回「设备仍在使用」），要么强制先复位设备。

另外撤销是 DFS + 逐页 unmap，8MB arena 可能耗时数毫秒：超过 N 页时分批执行并返回「进行中」，
避免撤销者被卡住、也避免长时间持锁。

### 5.8 授权形式与回收顺序

| 资源 | 对象类型 | 授权来源 | 回收时机 |
|---|---|---|---|
| MMIO 窗口 | `OBJ_DEVWIN` | boot 授权表 / `cap_mint` | CSpace 最后引用释放 / `cap_revoke` 时 unmap |
| DMA arena | `OBJ_UNTYPED` → `retype` | `cap_retype` | `refs` 归零 → 归还 untyped |
| 帧 / 共享页 | `OBJ_FRAME` | `cap_retype` / 服务建立连接时分配 | 最后一个能力销毁 + unmap |
| 中断 | `OBJ_IRQ` | 随设备窗口一起授予 | 服务注销（先 `irq_disable`） |
| 服务端点 | `OBJ_ENDPOINT` | boot / `cap_mint` | 端点 `refs` 归零 |
| 线程 | `OBJ_TCB` | 创建线程时 `retype` | 线程退出 + 最后一个引用释放 |

**回收顺序**必须是「先停中断 → 再 unmap 内存 → 最后摘名字 / 释放对象」，
否则会出现「内存已释放但硬件还在写」。

### 5.9 授权策略（默认拒绝、无身份环境权限、badge 只做审计）

cap 只解决「用什么句柄」，还必须定义「谁有权给」。缺了这节，5.6 的 `cap_get_service`
就退化成「谁都能拿」，模型空转。

**核心原则：能力路径不查身份。** 内核在 `mint` / `copy` / `invoke` 时只看能力的
`rights`，不看调用者 uid —— “谁是 root”不是万能钥匙。身份（uid/gid）只用于
POSIX 兼容层（`getuid/setuid`、文件权限）和审计日志，不参与授权判定。

| 规则 | 内容 |
|---|---|
| 默认拒绝 | 没有 cap 就是没有权限（`-CAP_NIL` / `-CAP_RIGHTS`），不做“先允许后审计” |
| 根能力来源 | **boot 授权表**（`/conf/foot.conf`）：内核在创建任务时把指定对象的能力装进它的 CSpace（`usbd` → `dwc2` 窗口 + IRQ；`gpud` → `v3d` 窗口）。普通进程初始只有 stdin/stdout 与 `OBJ_ENDPOINT(shell)` |
| 传递 | 只能沿 `mint`（本 CSpace，需 `MINT`）和 `copy`（跨 CSpace，需 `GRANT`）走，权限单调不增 |
| 按用户/角色授权 | 由**用户态 policy server** 负责：它持有 Endpoint 能力，收到请求后用 `mint` 发出受限能力。换授权策略不需要改内核 |
| 服务发现本身也要权限 | `OBJ_ENDPOINT` 就是“调用权”：没有该端点能力，连请求都发不出去，也无从枚举 |
| badge 只能授予方写 | badge 在内核 mint/copy 时写入，用户态不可改；服务端 `cap_info()` 读出来做鉴权与审计（**仅供参考，不作为内核授权依据**） |

> 反思：v1 曾在 `cap_get_mmio` 里按 `euid == 0` 放行。那是“基于身份的环境权限”，
> 与最小权限模型冲突——一旦某个服务被提权，它就自动获得全部设备。v2 已移除该判定。

### 5.10 CSpace 挂在 TCB 上：继承与生命周期

```
thread_t ──cspace*──> cspace_t { slots[], gens[], ref }
                         │
                         └──> kobject（DEVWIN / FRAME / ENDPOINT / IRQ / TCB）
```

CSpace 是**线程级**对象：每个 TCB 持有自己的 `cspace_t*`，句柄只在所属 CSpace 内有意义。
A 线程猜不到 B 线程的句柄，句柄天然隔离；跨线程/进程给能力必须显式 `copy`/IPC grant，
由内核做一次翻译。

#### 为什么挂 TCB 而不是 vm

早期实现挂在 `vmemory_t` 上，理由是“映射归页表、撤销要幂等”。挂 TCB 同样成立，
前提是把“共享”做成**显式引用计数**，而不是“同一个指针隐式共享”：

| 理由 | 说明 |
|---|---|
| 句柄隔离粒度最细 | 线程是调度与故障隔离的最小单位；一个线程崩溃/重启不污染别人的能力空间 |
| 与 seL4 语义一致 | CSpace 属于 TCB，创建线程、复制能力都是显式动作，审计台账 `(tid, cap)` 直接可查 |
| 撤销边界清晰 | `cspace->ref` 归零才撤销，多个 TCB 共享时由最后一个退出者收尾，不存在“谁先走谁撤”的竞态 |

#### 线程共享：显式引用计数

POSIX 语义要求同进程线程看到同一套 fd/服务句柄（一个线程 `open` 的服务，别的线程也能用）。
挂 TCB 后不能再靠“同一张表隐式共享”，改成共享同一个 `cspace_t` 并 `ref++`：

| 事件 | CSpace 处理 | 理由 |
|---|---|---|
| `clone(CLONE_VM)` | `ref++`，新 TCB 指向**同一个** `cspace_t` | 与 Linux 线程组共享 fd 表一致；`close` 对整个进程生效 |
| `fork` | `cspace_dup()`：复制整表，每个能力 `obj->refs++`，**去掉 `GRANT`/`MINT`/`REVOKE` 位** | 子进程继承句柄，但不能替父进程转授 |
| `vfork` | 借用父 CSpace（`ref++`），子进程 exec/exit 时归还 | 共享地址空间，句柄语义同 CLONE_VM |
| `exec` | 清空到基础集（stdin/stdout + 显式继承的能力） | 否则 exec 一个不可信程序 = 交出全部设备权限 |
| 线程退出 | `cspace_put()`：`ref--`，归零时撤销全部能力（含派生链）、unmap、`obj->refs--` | 最后一个使用者离开才真正回收 |
| 内核线程 | `cspace == NULL`，跳过全部 cap 校验 | 内核自己不需要能力 |

#### 凭据（cred）同样挂 TCB

`cred_t`（uid/euid/suid + gid 组）也从 `vmemory_t` 移到了 `thread_t`，规则与 CSpace 一致：

| 事件 | 处理 | 理由 |
|---|---|---|
| `clone(CLONE_VM)` | 共享同一份（`cred_ref`，`ref++`） | `setuid` 必须对整个进程生效（POSIX 线程组语义） |
| `fork` / `vfork` | `cred_dup()` 复制一份 | 子进程改凭据不能影响父进程 |
| `exec` | 保留（同一 TCB 继续用） | 与 Linux 一致 |
| 线程退出 | `cred_free()`，`ref` 归零才释放 | 共享时最后一个线程收尾 |
| 内核线程 | `cred == NULL`，`getuid()` 返回 0 | 内核不需要身份 |

**注意**：凭据只服务 POSIX 兼容与审计，cap 路径**不读它**（见 5.9）。这样把“安全状态”和
“身份状态”分开：撤掉 cred 不影响任何授权判定，改授权策略也不需要动 uid。

#### 与地址空间的销毁顺序

cap 撤销要在页表还在时 unmap，所以：

```
thread_exit → cspace_put（ref 归零 → 逐能力 ops->unmap）→ thread_destroy → vmemory_destroy
```

即 **CSpace 先于地址空间销毁**。v1 把撤销放在 `vmemory_destroy`（表挂 vm），v2 迁到
`thread_exit` 路径上；注意 `VM_SAME` 的线程共享同一份 vm，但 CSpace 的 `ref` 是独立计数的。

句柄位宽：`slot` 12 位（4096 槽）、`gen` 20 位。gen 回绕时该槽强制失效并重新分配，
避免长时间运行后被 ABA 命中。

## 六、故障隔离与恢复

### 6.1 调用超时

所有 `foot_wait` 必须带墙钟上限。超时语义：

- 服务方还在 = 请求可能仍会完成，客户端**不能重放**（设备状态已变）
- 服务方已死 = 内核负责把在飞请求标记为 `FOOT_EIO`，并唤醒所有等待者

### 6.2 服务崩溃检测

- 主路径：服务进程退出 → `close(/dev/foot)` → 内核 `service_close` 摘除名字并在共享页盖 `alive=0`
- 辅路径：心跳（每秒一次，3 次未到判定死亡），用于「进程活着但卡死」的情况

**现状（2026-10-31）**：`alive` 标记与 `client_stats().alive` 已就位（注册置 1、注销/退出清 0），
但「在飞请求立刻返回 `-3`」还没接上：服务进程退出会连同其 vm 一起销毁共享页，
而调用方手里是同一批物理帧的**裸映射**（尚无引用计数）⇒ 崩溃后调用方读到的可能是已被复用的页，
据此判死不可靠。所以现在仍是超时兜底（`client_call_ex` 返回 `-1`）；
快速失败要等共享页 refcount（`page_map_on` 侧加引用、任一侧 munmap/退出只减引用）落地后再接。

### 6.3 设备状态恢复责任的划分

| 场景 | 谁负责恢复 |
|---|---|
| 服务正常重启 | 服务自己重新 init 设备 |
| 服务崩溃、设备仍工作 | 新实例 init 时先 reset 设备（不能假设干净状态） |
| 设备挂死（GPU wedge、USB 掉线） | 内核模块提供「复位原语」，服务通过资源接口调用 |

所以内核里仍需要极少量与硬件相关的代码（复位、AXI 排空），这是混合内核的合理分工。

## 七、用户态驱动开发指南（以 csudusb 为例）

现状实录（`foot/driver/csudusb/main.c`）：

```c
sys = client_get("system");          /* 拿到资源服务 */
mmio_init();                         /* 5 次 SYS_MAP 映射 GPIO/DWC2/USB 窗口 */
usb_init();                          /* UsbInitialise + UsbCheckForChange */
while (1) {                          /* 事件循环：每秒轮询 */
  UsbCheckForChange();
  ...KeyboardPoll...
  usleep(1000000);
}
```

标准步骤（目标形态）：

1. **注册自己**：`client_regist("usbd")`，声明提供的方法（如 `USB_GET_EVENT`）
2. **申请资源（全部走 cap）**：`cap_map` 拿 MMIO 窗口；`cap_alloc_arena` 拿 DMA 缓冲；`cap_irq_wait` 等中断事件
3. **初始化设备**：写寄存器，跑硬件状态机
4. **事件循环**：`foot_wait_event(超时)` → 处理中断/请求 → `foot_reply(cid)`
5. **退出**：注销服务 → 停中断 → 释放 arena → 关 fd

清单（写在驱动里就少踩坑）：

- [ ] 不要用 `usleep(1000000)` 轮询，改成事件等待
- [ ] 热路径禁止 `printf`（串口是阻塞写，会拖死整个系统）
- [ ] 所有等待都要有超时
- [ ] 设备寄存器访问用 `volatile`，映射必须 `PAGE_DEV`（无缓存）
- [ ] 驱动自己崩溃后，下一个实例必须能处理「设备处于中间状态」

## 十一、性能模型

### 11.1 三个参照实现

| | LRPC（Liedtke 1993） | seL4 fastpath（2009/2014） | foot（现状 / 目标） |
|---|---|---|---|
| 核心手法 | 用户态 TCB、共享参数栈、lazy scheduling、direct process switch、small address space | 单页消息（寄存器 + IPC buffer）、跳过 cap 遍历、跳过调度决策、call/reply 专用路径 | 共享物理页双映射、零拷贝、ring 队列、futex 唤醒 |
| 优化目标 | 同步小消息往返 | 同步小消息往返（可验证） | 大消息、批量、异步完成 |
| 陷入次数/往返 | 2（call + reply return） | 1~2（call fastpath + reply） | 目标 0（稳态）或 1（futex 唤醒） |
| 数据传递 | 寄存器 + 共享栈（同 VA） | 寄存器（≤ 4~8 个）+ 1 页 IPC buffer | 共享页（240B ~ 整帧），零拷贝 |

### 11.2 延迟预算

量级估算，误差 ±50%。依据：ARMv8 异常进入/退出成本、Cortex-A76 的 cache 层级
（L1 64KB / 私有 L2 512KB / DSU 共享 L3 2MB）、IPI 唤醒成本、以及上述论文的公开数据。
频率按 2.4GHz 折算（1 cycle ≈ 0.42ns）。

| 操作 | cycles | ns | 说明 |
|---|---|---|---|
| 空 syscall 往返 | 150~250 | 60~100 | 异常进入 + 保存/恢复通用寄存器 + 分发查表 |
| LRPC 一次调用 | 250~450 | 100~190 | 2 次陷入 + 直接切换 + 寄存器传参；原文在 486 上约 120 cycles，现代流水线更深 |
| seL4 call fastpath | 200~400 | 85~170 | 1 次陷入 + 无 cap 遍历 + 无调度决策；x86 原文约 300 cycles |
| futex wake → 对端被调度 | 400~800 | 170~340 | 1 次 syscall + 等待队列操作 + **IPI 到另一核** + 目标核调度入口 |
| 跨核 cache line 传递（DSU L3 命中） | 60~120 | 25~50 | 生产者写、消费者读同一行 |
| **foot 稳态快路径**（对端已 spin 在 `tail`） | **40~120** | 17~50 | 写 240B 到共享行 + `stlr` 推进 tail + 对端 `ldar` 看到，无陷入 |
| **foot 目标（futex 唤醒路径）** | **500~900** | 210~380 | ring 写入 + futex syscall + IPI + 调度 |
| **foot 当前实现**（`client.c:53-55`） | **~1.2 亿** | **50,000,000** | `usleep(500000)` 退避，比 seL4 fastpath 慢 **5 个数量级** |

### 11.3 关键差异

1. **陷入次数**：LRPC 2 次、seL4 1 次、foot 0 次（稳态）。foot 的理论优势成立的前提是
   **服务方在另一颗核上空转**，等于拿 1/4 的 CPU 换延迟。
2. **是否做调度决策**：LRPC 用 lazy scheduling 跳过完整调度器，seL4 fastpath 直接跳过。
   foot 的 0 陷入路径天然没有调度，但**唤醒路径**必须经过完整调度器 + IPI，
   这是它比 seL4 慢的主因（400~800 cycles 大部分花在 IPI 和目标核调度入口）。
3. **地址空间**：三者都不需要 TLB flush —— LRPC 靠 small address space，seL4 靠 ASID，
   foot 靠「双方各自映射同一物理页、从不切换页表」。
4. **数据规模**：LRPC/seL4 的 fastpath 都限制在小消息（寄存器/单页），传 1080p 帧要退到 slowpath
   （页映射或多次拷贝）。foot 传句柄、数据留在共享页，大消息场景有结构性优势。
5. **语义方向**：foot 的服务方是消费者、请求方是生产者，天然适合异步（提交后不等）；
   LRPC/seL4 的 call 语义强制同步。

### 11.4 按负载判断

| 负载 | 更优 | 原因 |
|---|---|---|
| 高频小消息同步 RPC（文件系统元数据等） | seL4 / LRPC | 200~400 cycles，且不需要服务方空转 |
| 大块数据（帧缓冲、顶点数组、纹理） | **foot** | 零拷贝 + 只传句柄；LRPC/seL4 要么拷贝要么建映射 |
| 批量提交（一帧 100 条 2D 命令） | **foot** | 一次提交带 100 条，RPC 次数从 100 降到 1 |
| 异步完成（GPU 乱序返回） | **foot** | `cid` 配对天然支持；LRPC/seL4 的 call 是同步的 |
| 硬实时（毫秒级截止） | seL4 | 有 WCET 保证；foot 的唤醒延迟有 IPI 抖动 |

对 1080p 桌面：一帧若有 100 次 2D 操作，即使每次 300 cycles（125ns），总开销也只有 12.5us，
占 16.7ms 预算的 0.07%。而当前的 50ms 轮询会让一帧变成 5 秒。所以：

> **要补的不是「把 300 cycles 降到 100」，而是「把 100 次 RPC 压成 1 次批量提交 +
> 把 50ms 轮询变成 2us 唤醒」。**

### 11.5 目标值（验收线）

| 指标 | 当前 | 目标 | 依据 |
|---|---|---|---|
| 空载唤醒往返（1KB 消息，跨核） | 50ms | **< 5us** | 500~900 cycles + 调度抖动 ≈ 1~3us |
| 稳态快路径（对端轮询） | 50ms | **< 200ns** | 40~120 cycles |
| 批量吞吐（64 条 2D 命令/提交） | N × 50ms | **单次提交 < 10us** | RPC 摊薄到 156ns/条 |
| 空闲 CPU 占用 | 0%（睡在 `usleep`） | **0%（睡在 futex）** | 不能靠 spin 省 CPU |
| 单服务最大并发请求 | 1（单槽） | **≥ 64（ring）** | `api_size` 从 1 改 64 |

### 11.6 设计结论

1. **不追 LRPC/seL4 的同步小消息路径**。它们已把这条线压到 200~400 cycles，foot 用共享页
   最多追平，还要付出「服务方空转」的代价。该抄的是它们的三个技巧：
   **跳过调度决策、小消息走寄存器、不 flush TLB** —— foot 在第三点上已天然具备。
2. **唤醒成本是主要瓶颈**，优化方向是「减少唤醒次数」而不是「加快单次唤醒」：
   批量提交 + 服务方批量处理 + 只在 ring 空/满时唤醒，可把唤醒开销摊薄到 1/64。
3. **保留按需 spin**：图形栈活跃期（连续帧）让服务方短时 spin（如 50us 后再睡），
   活跃期延迟 200ns、空闲期 0% CPU。这是 LRPC 的 lazy scheduling 思想在用户态的变体。

### 11.7 实测方法

用户态可直接读 `cntvct_el0`（需内核允许），在调用前后各取一次，把差值写进共享页的统计槽，
分三个口径：

| 口径 | 起点 → 终点 | 对应 11.2 的哪一行 |
|---|---|---|
| `submit` | 开始写消息 → tail 推进完成 | foot 稳态快路径 |
| `wake` | tail 推进 → 服务方读到并开始处理 | futex 唤醒路径 |
| `complete` | 提交 → 收到同 `cid` 的响应 | 端到端往返 |

注意：**测量时必须先关掉热路径日志**（`printf` 一次是毫秒级，测出来的是串口不是 IPC），
且要关中断或至少多次取中位数，避免 IPI/时钟中断抖动污染样本。

## 十二、设计缺点与改进

第八章列的是「实现 bug」，本节列的是**结构性缺点**——即使把 P0 全修完，这些仍然存在。
每条给「缺点 → 影响 → 改进」，最后列出**明确不修**的取舍。

### 12.1 安全与隔离

| # | 缺点 | 影响 | 改进 |
|---|---|---|---|
| 1 | `SYS_THREAD_MAP` 接受任意 `phy_addr`，不校验范围（`sysfn_thread.c:80-104`） | 用户态可以把**内核内存、页表、其它进程的页**映射进自己的地址空间 | ✅ 已修（阶段 4 第一批）：用户态调用必须先持 `OBJ_DEVWIN`，映射范围不在窗口内一律 `-1`；驱动器改走 `foot_cap_map`。内核线程（`upage == kpage`）不受限 |
| 2 | 共享页无方向约束，请求区与响应区重叠 | 服务端可改写请求、客户端可改写响应，出错时无法判断谁写坏 | 用两张 `OBJ_FRAME` 分别授予读/写权限（见 5.6），方向由页表权限强制，而不是靠约定 |
| 3 | 任何进程都能 `client_get` 任意服务并调任意方法 | 无权限模型，一个服务被攻破等于全部 | 由 `OBJ_ENDPOINT` + badge 解决（见 5.6）：服务端按 badge 鉴权，cap 只携带已授权的方法位图 |

### 12.2 数据通路

| # | 缺点 | 影响 | 改进 |
|---|---|---|---|
| 4 | 无背压 / 流控 | ring 满时行为未定义（当前是覆盖最后一槽），请求静默丢失 | ⚠️ 已有背压：槽位满时 `client_submit_ex` 返回 `-2`（不覆盖、不丢），生产者可等结果再提交；「在 `head` 上 `FUTEX_WAIT` 等空位」未做 |
| 5 | 单一 FIFO，无优先级 | 输入事件（要求 < 1ms）会被日志/后台任务阻塞 | 每优先级一条 ring（或 per-client 队列），唤醒时按优先级出队 |
| 6 | 服务端完全串行（`client_run` 单线程跑所有方法） | 一个慢方法（如 100ms 的模糊）卡住整个服务的输入响应 | 慢操作异步化：立即返回 `cid`，完成后投递响应；`client_run` 只做轻量派发 |
| 7 | 参数上限 128 字节且定长拷贝（`client.c:39`） | 大参数只能另开共享页，协议分裂；小参数读越界 | ✅ 已改 `api_t.len` + `MAX_ARGS_BUF=240`，按 `len` 拷贝；大对象仍按约定传句柄 |

### 12.3 生命周期与资源回收

| # | 缺点 | 影响 | 改进 |
|---|---|---|---|
| 5 | 注销时不回收共享页（`service.c:107` 只摘名字） | 每个注册过的服务泄漏一页，长期运行会耗尽 | ✅ 已修：`client_t` 记录 `apis` 与 `map_count`，注销且无外部映射时 `sys_munmap` + `kfree`；有外部映射时保守保留（等 refcount） |
| 6 | 无代次（generation） | 服务重启后 `id` 复用，客户端缓存的旧 id 连到新服务（协议不匹配） | `id = (generation << 16 | slot)`；`client_get` 返回代次，调用时校验 |
| 7 | 无配额 | 一个服务可注册多个名字把 `clients[]`（100）打满 | per-服务 名字数与共享页数上限；超限返回错误 |
| 8 | 无心跳 | 「进程活着但卡死」检测不出来，客户端只会等到超时 | ⚠️ 半成品：注册置 `alive=1`、注销/退出清 0，`client_stats().alive` 可读；周期心跳时间戳未做（快速判死还缺共享页 refcount，见 6.2） |

| # | 缺点 | 影响 | 改进 |
|---|---|---|---|
| 9 | 只有 `printf` | 无法回答「延迟多少、失败率多少、谁在拖慢」 | ✅ 共享页控制区带 4 个计数器（`req_total`/`timeout`/`err`/`max_lat_ms`），`client_stats()` 零系统调用读出；`/dev/foot/<name>` 的 `read` 仍返回 0（未做） |

### 12.5 cap 模型的已知风险

| # | 问题 | 后果 | 改法 |
|---|---|---|---|
| 11 | cap 表在内核堆里，而 `sys_thread_map` 可映射任意物理地址 | 用户态直接改写 cap 表，cap 形同虚设 | **必须先收权 `sys_thread_map`，cap 才成立**；两件事的顺序绑死（路线图阶段 4 与阶段 1） |
| 12 | 撤销是 DFS + 逐页 unmap，8MB arena 可能数毫秒 | 撤销者被卡住、长时间持锁 | 分批执行（每次 N 页）+ 返回「进行中」 |
| 13 | 句柄 32 位，原设计 gen 仅 16 位 | 65536 次复用后被 ABA 命中 | gen 提到 24 位（slot 8 位）；回绕时该槽强制失效 |
| 14 | cap 表锁在多核下成为热点 | 每帧 submit 都 invoke 会争锁 | cap 解析结果缓存到用户态：首调后直读共享页 / IOVA，后续不 invoke |
| 15 | 共享中断（GPIO bank、PCIe 共享线）无法用「属于某窗口」判定归属 | 这类设备授权不了 | `OBJ_IRQ` 支持共享 IRQ 组订阅，ISR 分发给组内各订阅者 |
| 16 | cap 表没有 dump 接口 | 「句柄无效 / 权限不足」是最难查的一类 bug | `/dev/foot/caps` 输出 slot / type / rights / badge / gen / object |
| 17 | 阶段 1~3（P0 修复、ring、futex）仍在用旧授权模型 | 这期间系统没有权限边界 | 明确标注为**开发期临时不安全态**，不进产品镜像 |

### 12.6 明确不做的取舍

| 不做 | 理由 |
|---|---|
| LRPC 式 direct process switch | 收益（省 200~400 cycles）远小于复杂度（需要内核线程切换原语、优先级反转处理），且图形负载不缺这几百 cycles（见 11.4） |
| 内核内消息语义校验 | 内核一旦理解消息内容，新增方法就要改内核，违背「内核只做路由」的初衷；`client_t` / `api_t` 在两侧各存一份定义是刻意的（内核与用户态库解耦，任一侧可独立演进），变更时两侧同批修改 |
| 每条消息 CRC | 成本（每帧几十条）大于收益；用「方向分离 + 长度校验」覆盖绝大多数误用 |
| 内核态驱动兜底 | 会把混合内核退化成宏内核；设备复位这类必须特权的操作以**资源接口**形式暴露即可（见 6.3） |
